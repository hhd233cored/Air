# 文章指标：500 并发用户与阶段耗时（2026-09-25）

## 方法

使用独立 `air-perf` 栈和虚构数据。5000 个账号先以 4 路并发登录，突发阶段最多 500 个用户同时执行「一次浏览、一次点赞」，共 10000 个写请求。限流仅在压测栈关闭。随后同一用户重复点赞 100 次。客户端统计从发起 `fetch` 到读取完整响应的 HTTP 耗时；QPS 按请求完成时间分桶。第二轮在相同条件下开启 `X-Perf-Timing: 1`，服务端仅在隔离栈返回 `Server-Timing`。登录准备阶段不计入写请求 QPS。

原始逐秒记录：[普通 500 并发](RAW-ARTICLE-METRICS-500.jsonl)、[启用阶段计时的 500 并发](RAW-ARTICLE-METRICS-500-TIMING.jsonl)。记录仅含请求统计与虚构文章计数，不含账号密码或 Cookie。

## 吞吐与正确性

| 试验 | 10000 次写请求用时 | 平均合计 QPS | 最高 1 秒 QPS | 浏览 p50 / p95 | 点赞 p50 / p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 之前 250 并发 | 13.8 s | 约 725 | 未记录 | 319 / 624.9 ms | 305.9 / 614.4 ms |
| 500 并发 | 12.1 s | 828.2 | 1002 | 562.2 / 873.4 ms | 560.8 / 823.1 ms |
| 500 并发，开启阶段计时 | 12.0 s | 832.5 | 995 | 559.5 / 924.8 ms | 550.5 / 851.0 ms |

500 并发无计时轮中，浏览和点赞各 5000 次全部成功，分别约 414 QPS；100 次重复点赞全部返回 `changed=false`。计时轮也有 10000 次成功写入，分别约 416 QPS，重复点赞无新增。两轮各自收敛到 PostgreSQL 浏览事实 5000、点赞关系 5000、已处理事件 10000、统计 5000/5000；未发布 outbox、RabbitMQ 工作队列和死信队列均为 0。这里的“500 并发”是客户端最多同时处理 500 个用户，不是 5000 个同时连接。

从 250 提升到 500 并发后，平均合计 QPS 提高约 14%，但单请求中位延迟上升约 75%–83%。峰值 QPS 是单个完整一秒桶的完成量，不是可持续吞吐。

## 分段计时：500 并发、5000 个样本/接口

下表是 **平均毫秒**，括号中为 p50 / p95。`transaction` 包含事实 INSERT、outbox INSERT 与 COMMIT；`controller` 又包含参数校验、文章查询与事务。因此各行不能直接相加。

| 阶段 | 浏览 POST | 点赞 PUT | 测量边界 |
| --- | ---: | ---: | --- |
| 参数校验 | <0.01（<0.1 / <0.1） | 无需解析 UUID | 控制器调用后的 Java 参数处理 |
| 文章查询 | 88.06（72.1 / 231.7） | 86.97（72.5 / 225.2） | `publishedArticleId` 调用，包含连接池等待与 SQL |
| 事实 INSERT | 0.79（0.7 / 1.5） | 0.73（0.7 / 1.2） | JDBC `update()`，连接已在事务中获取 |
| outbox INSERT | 0.58（0.5 / 1.0） | 0.56（0.5 / 0.9） | JDBC `update()` |
| 近似 COMMIT | 5.27（4.9 / 7.8） | 5.13（4.8 / 7.2） | Spring `beforeCommit` 到 `afterCommit`；含回调开销 |
| 事务调用整体 | 45.91（7.9 / 181.3） | 47.73（7.7 / 179.0） | 调用事务代理到返回，含连接池/锁等待与 COMMIT |
| 控制器调用段 | 133.98（109.2 / 325.1） | 134.71（114.7 / 315.5） | 进入指标控制器到构造响应；不含 JSON 写出 |
| 控制器外合并耗时 | 460.36（432.3 / 716.6） | 437.61（429.3 / 615.1） | 客户端 HTTP 耗时减控制器调用段 |
| 客户端 HTTP 全程 | **约 594.34**（559.5 / 924.8） | **约 572.32**（550.5 / 851.0） | 发起 fetch 到完整读取响应 |

“控制器外合并耗时”同时包括客户端/服务器排队、网络、Spring Security、Session、CSRF、Redis 往返、JSON 序列化等，**不能直接称为认证耗时**。本轮没有在这些框架内部逐个打点，因此不能可靠地给出「认证 5 ms、CSRF 1 ms、Redis若干毫秒、序列化若干毫秒」这样的拆分。Redis `INFO commandstats` 在包含登录准备与突发阶段的窗口里显示：`HGETALL` 平均服务器执行 11.6 微秒、`HMSET` 9.75 微秒、`PEXPIRE` 8.4 微秒；这些数不含网络、排队和 Spring Session 工作，不能转换成每个 HTTP 请求的 Redis 耗时。

文章查询和事务调用的尾延迟较高，而 INSERT 本身很短，提示连接池获取、并发调度与事务等待比单条 SQL 执行更值得继续排查。这是从阶段计时得到的**推断**；要确定各自贡献，需要再采集 Hikari 活跃/等待连接数、PostgreSQL 等待事件和服务端请求队列。压测时前端脚本、Docker 容器都运行在同一台机器，结果只用于本机比较。
