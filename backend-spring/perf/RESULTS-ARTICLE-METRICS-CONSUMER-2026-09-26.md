# 文章指标消费者拆测（2026-09-26）

## 结论

当前消费端最大的执行开销是**每条事件独立事务提交**。请求结束后的样本中，提交近似段占消费执行时间 **58.0%–71.2%**；`event` 查询约 **0.34–0.38 ms**，Redis 删除约 **0.48–0.56 ms**，借连接接近零。点赞统计重算约 **1.62 ms**，高于浏览计数更新的 **0.35 ms**，是第二个值得优化的 SQL 段。

下一步优先验证批量消费共用一次事务提交，并按文章合并统计更新与缓存失效。仍需保留防重记录、提交后 ACK 和失败重投语义。本轮完成计时和复测，尚未实施消费批量化。

## 方法与计时边界

新建隔离 Compose 项目 `air-perf-consumer`，应用本机端口 18089、RabbitMQ 管理端口 18090，独立 PostgreSQL、Redis、RabbitMQ 卷。使用当前源码和批量发布标记实现，V1004 已应用，加载 2000 篇虚构文章、5000 个虚构账号。关闭限流，客户端并发 100，文章消费者仍为 1 个、prefetch 100。先执行 5000 次有效浏览与 5000 次首次点赞，完全排空后再执行 10000 次匿名有效浏览。登录准备独立计时。

只有 `PERF_TIMING_ENABLED=true` 时采样，正常配置默认关闭。消费者逐条保存数值样本，每秒由定时任务按最多 100 条一组输出；保留逐条样本，按 VIEW、LIKE 和消费开始时间直接计算分位数。原始记录不包含消息 ID、文章 ID、消息正文或凭据。

| 字段 | 范围 |
| --- | --- |
| `eventMs` | 查询 outbox 事件的整个仓储调用，含借连接、SQL、结果映射 |
| `eventAcquireMs` | 上述调用内 Hikari 借连接时间 |
| `applyCallMs` | Spring 事务代理的完整 `apply` 调用，包括事务开始、方法体、提交和清理 |
| `applyAcquireMs` | 上述调用内 Hikari 借连接时间，通常发生于方法体开始前 |
| `applyBodyMs` | `apply` 方法体，含防重与统计更新 SQL，不含代理在方法返回后的提交 |
| `processedSqlMs` | 防重 INSERT 的 JDBC 调用 |
| `statsSqlMs` | 浏览计数 UPSERT，或点赞关系 COUNT 与统计 UPSERT 的 JDBC 调用 |
| `commitApproxMs` | Spring `beforeCommit` 至 `afterCommit`，含 JDBC COMMIT 和回调开销 |
| `applyOtherMs` | `applyCall` 减去方法体、借连接及提交近似值的剩余时间，主要包含事务开始/清理等，不是某一组件的纯耗时 |
| `cacheMs` | 提交之后 Redis 缓存删除的整个调用，含客户端、连接、网络及失败日志处理 |
| `ackMs` | ACK/NACK/Reject 客户端调用，不代表收到 RabbitMQ 服务端确认的时间 |
| `cycleMs` | 消费监听方法入口至确认调用完成；不含此前排队、框架调度和之后分组日志输出 |

`eventMs`、`applyCallMs`、`cacheMs`、解码、确认及剩余时间可作为消费执行的互斥阶段；SQL、提交、借连接属于嵌套子段，不能重复相加。所有 SQL 时间均为客户端调用边界，不是 PostgreSQL 内部纯执行时间。提交分位数只使用观测到成功提交的样本，回滚单独计数。

汇总中的 `burst-or-overlap` 指 HTTP 突发结束前开始的消费，可能跨越结束边界；`after-burst` 指之后才开始的消费。不把跨界样本强行拆分。时间轴探针与日志定时任务有开销，RabbitMQ 管理统计也存在刷新延迟。

## 代码与正确性验证

添加 [消费者计时](../src/main/java/org/airchord/backend/metrics/ArticleMetricConsumerTiming.java)，在 [监听器](../src/main/java/org/airchord/backend/metrics/ArticleMetricConsumer.java) 记录外层调用，在 [仓储](../src/main/java/org/airchord/backend/metrics/ArticleMetricRepository.java) 记录事务方法体、SQL 与提交回调，并在 [缓存](../src/main/java/org/airchord/backend/metrics/ArticleStatsCache.java) 记录已捕获的 Redis 删除失败。

本轮保留已有消费业务逻辑：数据库处理标记和统计同事务，提交后删除缓存，再 ACK；重复消费只 ACK；数据库异常重投；格式错误或缺少 outbox 的消息送入死信队列；Redis 删除失败由短 TTL 结束旧快照。未调整消费者并发或事务批次。

Java 打包及镜像构建成功。在 Linux 构建容器中运行消费者、发布器和文章指标相关测试，**20 项通过，失败/错误/跳过均为 0**。覆盖计时开关两种配置下的成功消费、重复消费、数据库异常重投、格式/缺失事件拒绝，以及 Redis 删除失败后仍 ACK。PostgreSQL 随机独立 schema 验证真实 Spring 事务代理的提交回调、重复事件跳过统计 SQL、回滚状态与防重记录回滚。测试随机 schema 已清理。测试日志见 [相关测试](../target/consumer-tests-2026-09-26.log)。这不是全量测试套件结果。

## 消费结果：请求结束后

完整采集 **20000 条**消费样本，全部为 `APPLIED`、`COMMITTED`，每条均观测到 1 次成功提交和 1 次缓存失效尝试；重复、拒绝、重投和 Redis 删除失败均为 **0**。混合轮准确区分 5000 条 VIEW、5000 条 LIKE；匿名轮为 10000 条 VIEW。

下表使用请求结束后才开始的消费，排除突发期间显著的池等待。时间单位为 ms，每条消息均值；嵌套行不与 `applyCall` 再次相加。

| 阶段 | 混合 VIEW（4891 条） | 混合 LIKE（4931 条） | 匿名 VIEW（9833 条） |
| --- | ---: | ---: | ---: |
| `event` 查询 | 0.382 | 0.378 | 0.336 |
| 完整 `applyCall` | 5.274 | 6.623 | 5.048 |
| ↳ `apply` 方法体 | 0.843 | 2.104 | 0.760 |
| ↳ 防重 INSERT | 0.490 | 0.481 | 0.434 |
| ↳ 统计更新 SQL | 0.348 | 1.618 | 0.322 |
| ↳ 提交近似段 | **4.376** | **4.463** | **4.248** |
| ↳ 事务剩余开销 | 0.054 | 0.056 | 0.040 |
| Redis 删除 | 0.540 | 0.556 | 0.480 |
| ACK 调用 | 0.102 | 0.104 | 0.085 |
| 整条消费执行 | **6.332** | **7.696** | **5.963** |
| 提交近似段占整条执行比例 | **69.11%** | **57.99%** | **71.24%** |

其中防重与统计 SQL 属于方法体，方法体、提交、借连接和清理属于完整事务调用。“事务剩余开销”是按差值计算的近似剩余，不是独立组件测量。

这些样本的分位数直接由逐条记录计算：

| 阶段 p95（ms） | 混合 VIEW | 混合 LIKE | 匿名 VIEW |
| --- | ---: | ---: | ---: |
| `event` 查询 | 0.656 | 0.660 | 0.589 |
| 完整 `applyCall` | 7.242 | 8.925 | 6.769 |
| 防重 INSERT | 0.860 | 0.835 | 0.757 |
| 统计更新 SQL | 0.602 | 2.657 | 0.564 |
| 提交近似段 | 6.108 | 6.107 | 5.759 |
| Redis 删除 | 0.927 | 0.950 | 0.828 |
| 整条消费执行 | 8.665 | 10.406 | 8.042 |

请求结束后，混合 9822 条的 `event` 借连接累计 **8.849 ms**、`apply` 借连接累计 **3.275 ms**；匿名 9833 条分别为 **7.334 / 2.326 ms**。该阶段的数十秒排空无法由连接池等待解释。混合队列处理约 **140.6 条/s**，匿名约 **166.3 条/s**（样本数除以这一阶段首末消费跨度），与单消费者每条执行约 6–7 ms 的量级一致。

点赞统计 SQL 仍从 `article_likes` 重算当前文章点赞数，包含两处 COUNT 表达式，以保持取消赞和重新点赞消息乱序时的正确性；本轮没有进一步把 COUNT、UPSERT 和客户端开销拆开。其整体调用时间比混合浏览统计 SQL 高约 4.65 倍，提交近似段依然是最大单段。

## 突发期间与全部样本

混合轮有 178 条消费在 HTTP 突发结束前开始，其消费执行均值 **55.547 ms**，`event` 调用均值 **30.621 ms**，其中借连接 **29.781 ms**；`apply` 借连接均值 **13.632 ms**。这一小部分样本具有明显的池争用。剩余 9822 条进入无明显池等待的持续排空阶段。

| 全部样本 | 混合 VIEW | 混合 LIKE | 匿名 VIEW |
| --- | ---: | ---: | ---: |
| 样本数 | 5000 | 5000 | 10000 |
| 消费执行均值 / p95 | 7.690 / 9.230 ms | 8.072 / 10.731 ms | 6.803 / 8.367 ms |
| `event` 均值 | 1.272 ms | 0.564 ms | 0.910 ms |
| 完整 `applyCall` 均值 | 5.708 ms | 6.804 ms | 5.306 ms |
| 提交近似段均值 | 4.438 ms | 4.493 ms | 4.299 ms |
| Redis 删除均值 | 0.557 ms | 0.561 ms | 0.487 ms |

混合轮消费执行累计 **78.808 s**，其中提交近似段 **44.657 s**；匿名轮分别为 **68.027 / 42.988 s**。第一条开始到最后一条完成的消费跨度为 **79.812 / 68.547 s**。消费跨度还包含监听器外部调度与样本收集等间隙，不能与各调用累计时间完全等同。

PostgreSQL 采样观察到 `IO:WalSync`、`LWLock:WALWrite`，混合轮还观察到 `IO:WalWrite`；没有采到 Lock 等待。这与提交阶段占主要开销的结果一致，但不能仅凭抽样量化 WAL、磁盘、网络、驱动或回调各自占比，也不代表所有瞬时锁等待都不存在。

## 下一步

优先试验一个有界消费批次共用一次事务提交，例如先以 50 或 100 条作为 A/B 起点。数据库必须先用事件 ID 防重，只对首次处理的事件更新统计；成功提交后再失效缓存并 ACK。事务失败要保留重投机会，重复投递不能重复计数。

同一批中可按文章合并 VIEW 增量，LIKE 从真实点赞关系按文章重算一次，并对每篇文章失效缓存一次。随后再测 `event` 批量读取、SQL 和提交的占比。增加消费并发时需同时测热点文章统计行的锁等待，不应直接用并发数推算吞吐。

本轮增加了逐条采样、定时分组日志及探针，且为同机先后单次试跑；开发栈也在运行，机器资源未固定。与上一轮整体时长的变化不构成严格优化 A/B，也不能据此估计线上容量。匿名轮使用混合轮完全排空后的同一隔离数据库。
