# 文章指标与秒杀示例：同机同客户端对照（2026-09-25）

## 测法

使用 `perf/article-metrics-compare.mjs`、Node `fetch`、100 个并发工作者，每轮 10000 次请求。Air 混合场景中，每个工作者按用户先浏览再点赞；其他场景每个工作者连续发独立请求，因此到达节奏并不完全相同。Air 运行在单独的 `air-perf` Compose 栈，限流关闭，阶段计时开启。有效点赞使用 5000 个事先登录的虚构账号；登录耗时 82.2 秒，未计入突发 RPS。有效写从全新 `air-perf` 数据卷开始，匿名浏览在其后运行，重复点赞在先前的小样本环境运行。所有场景共用本机 CPU、内存与 Docker；没有固定资源限额。

秒杀项目使用下载目录中的原始 Go 源码编译；Go 程序和单独 Redis 共享一个容器网络，使代码中硬编码的 `:6379` 只连接隔离 Redis。初始库存 10000，本地库存上限 150。没有修改下载目录或开发 Redis。秒杀接口监听本机 3005，Air 监听本机 18081。两个后端都由同一个 Node 脚本发压，但业务语义、持久化和认证要求不同。

## 业务结果与 HTTP 耗时

| 场景 | 业务结果 | RPS | p50 | p95 | p99 |
| --- | --- | ---: | ---: | ---: | ---: |
| Air 混合有效写 | 浏览 5000、点赞 5000，全部 `changed=true` | 689.5 | 133.8 ms | 269.1 ms | 353.3 ms |
| Air 重复点赞 | 10000 次均 `changed=false` | 1066.7 | 85.6 ms | 176.5 ms | 227.9 ms |
| Air 匿名有效浏览 | 10000 次均 `changed=true` | 750.4 | 116.3 ms | 302.9 ms | 438.5 ms |
| 秒杀，初始库存 | 150 次购票成功、9850 次售罄 | 3010.2 | 27.8 ms | 50.5 ms | 141.9 ms |
| 秒杀，已售罄 | 10000 次均售罄 | 3095.4 | 27.3 ms | 59.2 ms | 112.9 ms |

秒杀两轮的 HTTP 状态均为 10000 次 `200`；业务结果通过响应 JSON 的 `code` 分辨。独立 Redis 的最终销量为 150。Air 的有效写均为 HTTP 浏览 `202`、点赞 `200`；重复点赞虽是 `200`，不会新增事实或 outbox。Air 最终 PostgreSQL 核对：浏览事实 15000（混合 5000 + 匿名 10000）、点赞关系 5000、已处理事件 20000、未发布 outbox 0，统计 15000/5000。两次有效写的统计轮询均在第 81 次看到目标值，表明 HTTP 接收完成后仍需等待异步读模型收敛；不是 81 秒的单次 HTTP 延迟。

原始逐行输出保存在本机 `target/compare-mixed.jsonl`、`target/compare-duplicate.jsonl`、`target/compare-anonymous.jsonl`、`target/compare-spike.jsonl` 和 `target/compare-spike-soldout.jsonl`。这些本机输出不含密码或 Cookie。

## Air 等待采样与阶段计时

| 场景 | Hikari 最大活跃 / 待连接 | PostgreSQL Lock / IO / 其他活动等待采样最大值 | `preController` 均值 | 文章查询调用均值 | 事务调用均值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 混合有效写 | 10 / 88 | 0 / 1 / 7 | 50.43 ms | 50.96 ms | 32.84 ms |
| 重复点赞 | 10 / 72 | 0 / 0 / 0 | 23.62 ms | 21.26 ms | 8.99 ms |
| 匿名有效浏览 | 10 / 90 | 0 / 1 / 8 | 1.13 ms | 90.71 ms | 31.66 ms |

本轮 Hikari 活跃连接最多采到 10，同时三个场景均采到大量线程等待连接。这说明存在连接池前排队，但还不能判断增加连接数能否提升整体吞吐。`preController` 从最早的 Servlet 过滤器到控制器动作开始；已登录场景额外经过 Session 和账号状态核对，匿名浏览没有已登录账号核对。文章查询调用包含获取连接时间，不能把其均值解释成单条 SQL 的执行时间。采样中未见 PostgreSQL Lock 等待，但混合和匿名场景出现了其他 PostgreSQL 等待；该轮原始输出只保存了分类计数，之后探针已补充活动 `wait_event` 名称。采样也可能漏掉短暂锁等待。探针与业务共用连接池，`dbProbeMs` 同时包含连接池等待和 `pg_stat_activity` 查询，不能当作 PostgreSQL 查询耗时。

秒杀项目的第二轮售罄路径约为 Air 重复点赞路径的 2.9 倍吞吐；秒杀路径主要在内存判断后返回，没有登录、CSRF、用户关系查询、数据库事务或可恢复事件。Air 混合有效写与秒杀首轮总 RPS 的差异也不能当作同等有效写的性能倍率。下一步应针对 Air 已观察到的连接池排队，分别测量认证中的账号查询、文章查询的取连接时间，以及消费者与 HTTP 请求竞争连接的程度，再决定是否调整连接池、SQL 或读模型处理方式。

## 后续只读执行计划核对

在已停止负载的隔离 PostgreSQL 中，对与代码相同的查询执行 `EXPLAIN (ANALYZE, BUFFERS)`：

| 查询 | 计划 | 单次数据库执行时间 |
| --- | --- | ---: |
| `users WHERE id = 1005`，查询认证使用的字段 | `users_pkey` Index Scan | 0.115 ms |
| `content_items` 原始 `lower(trim(slug))` 条件 | Seq Scan；约 4004 行中找到 1 行 | 首次 5.186 ms；缓存变热后 2.433 ms |
| `content_items` 改用 `slug = 'perf-article-1'` 的只读对照 | `content_items_type_slug_unique` Index Scan | 0.169 ms |

隔离库 4004 个 slug 均已是去空格、小写形式；这不证明其他环境的历史数据也满足该条件。上述时间是在没有压测并发时测得的数据库内部执行时间，不能与包含连接池等待的 `preController` 或 `lookup` 时间等同。账号 SQL 本身已经按主键索引查找；文章 SQL 的列函数导致现有 `(content_type, slug)` 唯一索引无法承担精确 slug 查找。先核对所有环境的 slug 语义并做相同负载的改前、改后测试，比直接增大连接池更容易确认收益。
