# 文章指标连接与异步积压时间轴（2026-09-26）

## 方法

在新建的 `air-perf-timeline` 隔离 Compose 项目中，以当前源码和独立 PostgreSQL、Redis、RabbitMQ 卷运行；应用端口为本机 18084，RabbitMQ 管理 API 仅映射到本机 18083。V1004 索引已应用。加载 2000 篇虚构文章与 5000 个虚构账号，限流关闭，100 个并发工作者。先执行 5000 次首次浏览加 5000 次首次点赞，再执行 10000 次匿名有效浏览。登录准备时间不计入突发阶段。

只在 `PERF_TIMING_ENABLED=true` 时注册 Hikari 指标回调。每个请求的 `dbAcquirePre` 是进入控制器前借连接耗时总和，`dbAcquireController` 是控制器内借连接耗时总和；一个请求可能多次借连接。这是 Hikari 借连接回调测得的时间，包含池等待、连接准备等，不含连接到手后的 SQL 执行。客户端按响应完成时间逐秒汇总。应用探针约每 500 ms 读取 Hikari 状态、PostgreSQL 等待与未发布 outbox 数；同一采样循环读取 RabbitMQ `messages_ready`、`messages_unacknowledged`。每条原始记录保留各自的毫秒级 Unix 时间戳。探针和业务共用数据库池，会有少量采样开销；RabbitMQ 管理统计也可能滞后。

原始逐行 JSON：[混合有效写](../target/timeline-mixed-2026-09-26.jsonl)、[匿名有效浏览](../target/timeline-anonymous-2026-09-26.jsonl)。文件在本机被 Git 忽略，不含密码、Cookie 或消息正文。

## 同一时间轴：outbox 与 RabbitMQ

下表时间 `t` 从突发开始算起。队列数为 ready + unacked；各点取离指定秒数最近的样本。管理 API 与应用探针独立完成，所以同一行可能有少量时间偏差。

| t | 混合：待发布 outbox / 队列 / Hikari 待连接 | 匿名：待发布 outbox / 队列 / Hikari 待连接 |
| ---: | ---: | ---: |
| 约 5 s | 4384 / 0 / 81 | 6157 / 0 / 74 |
| 约 10 s | 9238 / 314 / 83 | 9027 / 309 / 0 |
| 约 20 s | 8093 / 544 / 0 | 7545 / 245 / 0 |
| 约 40 s | 5761 / 405 / 0 | 4931 / 79 / 0 |
| 约 60 s | 3474 / 191 / 0 | 2554 / 0 / 0 |
| 约 80 s | 1095 / 88 / 0 | 152 / 66 / 0 |

混合场景 outbox 峰值 9335（约 10.4 s），队列峰值 606（约 11.4 s）；约 89.6 s 时 outbox 首次采到 0，队列当时仍报 111。该轮脚本在统计收敛时停止采样，之后单独核对队列为 0。匿名场景 outbox 峰值 9446（约 7.1 s），队列峰值 342（约 12.8 s）；约 81.8 s 时 outbox 首次采到 0，约 83.4 s 连续两次采到 outbox 与队列均为 0。中途队列可能短暂为 0，不代表整个流水线已排空。

HTTP 突发结束后，Hikari 待连接很快归零，但 outbox 仍保留数千条并继续下降。采样中的 RabbitMQ 队列始终远小于 outbox 待发布数，说明这次异步收敛的主要积压位于“数据库 outbox 尚未标记发布”这一侧。`published_at` 是发布确认后的数据库标记，不能仅凭现有记录拆分 `claimOutbox`、发送与确认、逐条 `markPublished` 的耗时，也不能把队列瞬时值当作每条消息的准确入队时间。

## 正确性与下一步

最终目标文章的浏览事实 15000、点赞关系 5000、统计 15000/5000；未发布 outbox 0，文章工作队列与死信队列 ready/unacked 均为 0。已处理事件共 20001，其中 1 条是本轮在示例文章 `learning-spring` 上验证探针时产生的事件，其余 20000 条来自两轮目标文章压测。

下一步最值得拆解的是 outbox 发布器每批 `claimOutbox(200)`、RabbitMQ confirm 和逐条 `markPublished` 的耗时与吞吐。HTTP 侧则应针对连接池排队做隔离 A/B，观察 PostgreSQL WAL 等待、事务吞吐和尾延迟，再决定是否调整池大小。当前证据不支持把文章 SQL 或 Redis Lua 当成有效写的首要优化点。
