# 2026-09-25 搜索 SQL 优化对照

## 改动与核对

公开 `/api/v1/search` 保留全文检索与字面包含匹配的并集，以及原有总数、分页和排序。`V1002` 新增数据库触发器维护的小写字面搜索列，并在已发布、未删除记录上建立 `pg_trgm` GIN 索引。`ALL` 类型的 SQL 不再包含恒真的类型判断。

`SearchSqlIntegrationTest` 在独立 schema 中把新 SQL 与改动前的 SQL 对照，覆盖中文短词、英文大小写、`%`、`_`、`!`、反斜杠、草稿、软删除、类型和分页；修改标题、标签与正文后再次核对。完整 Maven 测试为 26 项，通过 26 项。

## 执行计划

在独立 `air-perf` PostgreSQL 18.6 中载入 2,000 篇文章、2,000 条说说及 4 条参照内容，执行 `ANALYZE`。以下是同一数据库、同一词的 `COUNT(*)` 单次 `EXPLAIN (ANALYZE, BUFFERS)`；只是 SQL 层对照，不能直接推算整个接口的延迟。

| 查询词 | 改动前 | 改动后 | 观察 |
| --- | ---: | ---: | --- |
| `不存在的词`，无匹配 | 24.149 ms | 0.237 ms | 原查询顺序扫描 4,004 行；新查询用全文 GIN 与 trigram GIN 的 `BitmapOr` |
| `Spring`，匹配约 4,001 行 | 5.956 ms | 6.906 ms | 两者都顺序扫描；高命中率下索引没有优势，单次测量不表明稳定回退幅度 |

这批数据上的字面搜索索引约 4,432 kB，全文索引约 1,088 kB；新列还占用表空间，并在写入时增加触发器和索引维护成本。关键词少于三个字符时，trigram 索引可提取的信息有限，仍需实测。

## 同脚本接口压测

与[首轮记录](RESULTS-2026-09-25.md)使用相同主机、虚构数据量、`search-high` 脚本和每档 30 秒。请求一半搜索常见词 `Spring`，一半搜索无匹配词 `不存在的词`；两次运行不是严格受控的 A/B，主机和容器缓存状态可能不同。新版原始结果在 [JSONL](results-search-after-2026-09-25.jsonl)。

| 目标 RPS | 改动前实际 RPS / p95 | 改动后实际 RPS / p95 | 改动后请求结果 |
| ---: | ---: | ---: | --- |
| 200 | 199.5 / 84.3 ms | 199.8 / 35.3 ms | 5,999 次 200，丢弃 0 |
| 240 | 238.4 / 178.1 ms | 239.7 / 31.1 ms | 7,196 次 200，丢弃 0 |
| 320 | 228.9 / 1,916.9 ms | 319.7 / 32.6 ms | 9,591 次 200，丢弃 0；旧版丢弃 2,553 个计划请求 |
| 400 | 未测 | 399.6 / 34.0 ms | 11,998 次 200，丢弃 0 |

这个负载下，消除无匹配词逐行拼接和扫描的成本让接口在 400 RPS 档仍保持稳定。容量结论只适用于本机单实例、这批虚构数据和这种关键词比例；不能把 400 RPS 当作生产承诺，也不能据此认为常见词搜索同样加速。
