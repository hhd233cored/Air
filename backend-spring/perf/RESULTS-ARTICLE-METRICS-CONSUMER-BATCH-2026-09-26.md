# 文章指标有界批量消费实现与复测（2026-09-26）

## 实现

沿用 [消费者拆测](RESULTS-ARTICLE-METRICS-CONSUMER-2026-09-26.md) 的下一步：单消费者每批最多 100 条，一次事务提交，聚批最多等待 100 ms。`ARTICLE_METRIC_CONSUMER_BATCH_SIZE` 支持 1–200，`ARTICLE_METRIC_CONSUMER_BATCH_WAIT_MS` 支持 1–1000 ms，越界配置启动失败；prefetch 与批大小一致。发布器仍是已完成的批量发布标记版本。

1. 逐条解析消息；格式或版本错误单独拒绝到 DLQ。
2. 去重事件 ID 后一次查询 outbox；不存在的 ID 单独拒绝。
3. 一个事务用 `INSERT ... ON CONFLICT DO NOTHING RETURNING event_id` 批量建立防重标记。只处理首次返回的 ID，批内与跨批重复事件都不再次更新统计。
4. 按文章合并 VIEW 次数，LIKE 从真实 `article_likes` 重算。每篇文章执行一次 UPSERT，COUNT 在插入的 CASE 表达式中计算一次，再由 `EXCLUDED.like_count` 更新冲突行；只有 VIEW 时保留已有点赞数。文章更新顺序固定，降低未来多消费者反向取锁的风险。
5. 事务代理成功返回后，每篇变化文章失效一次 Redis 计数缓存，逐条 ACK。DB 查询或事务失败则对剩余有效消息 NACK/requeue。ACK 的 IOException 交由监听器恢复连接，避免再 NACK 已 ACK 的 tag。

未新增迁移。数据库中的浏览事实、点赞关系、outbox 和 processed 唯一键仍是可靠性依据；VIEW 延续原逻辑，每个首次处理的浏览事件加一。Redis 删除失败仍记录错误并依靠 30–35 s TTL 回源，不回滚已提交数据。默认关闭压测采样。

消费者支持本项目发布器的单条消息格式。Spring AMQP 4.1.1 的 consumerBatchEnabled 会在工厂与容器初始化中自动开启生产者拆包，普通 setDeBatchingEnabled(false) 会被覆盖。因此消费者检查批内重复 deliveryTag：生产者批消息共享 tag 时整条拒绝一次到 DLQ，不处理其中任何片段，其余正常消息继续；防止覆盖片段后误 ACK 整条消息。低流量聚批等待发生在监听方法入口之前，不计入 `cycleMs`；端到端等待还包含发布器轮询及队列停留。

## 验证

Docker Java 21 环境对当前挂载源代码运行 29 个测试：消费者 18、发布器 8、PostgreSQL 集成 3，全部通过、无跳过。

- 批内重复与先前已处理的事件不重复计数，全重复批次不更新统计和缓存。
- 两篇文章在同一批处理；让第二篇统计行违反 CHECK，确认第一篇更新与新 processed 标记一起回滚，所有有效消息 NACK。
- 解除故障后重投，一次提交、每篇一次缓存失效、每条 ACK；缓存失效时其他数据库连接已经能看到整批结果。
- 点赞、取消赞、重新点赞事件逆序混入批次，最终点赞数仍等于真实关系数。
- 格式错误与不存在的事件同正常消息混批时，单独拒绝，其余继续处理。
- 两个有效 JSON 片段共享 deliveryTag 时，整条只拒绝一次、不应用任何片段、不 ACK 该 tag；同批的正常消息仍提交并 ACK。
- 提交调用失败时不失效缓存、不 ACK；ACK 中途断连不 NACK 已确认 tag。
- Redis 删除故障不丢失提交结果，仍 ACK；采样开关开启与关闭均覆盖。

初轮测试日志在 `target/consumer-batch-tests-2026-09-26.log`，最终回归在 `target/consumer-batch-tests-final-2026-09-26.log`；故障注入日志中的异常是测试预期。

## 复测方法与边界

新建 `air-perf-consumer-batch` Compose 项目，独立 PostgreSQL、Redis、RabbitMQ，HTTP 18091、MQ 管理 API 18092。相同虚构夹具：2000 篇文章、5000 用户。关闭业务限流，开启 HTTP、发布器、消费者采样和 500 ms 等待探针。混合有效写与匿名浏览各 10000 请求、并发 100；匿名轮在混合轮完全排空后运行。

基线为前述逐条消费者记录；同机先后单次试跑，开发栈继续运行、资源未固定，不能当作随机多轮严格 A/B 或线上容量。新样本以批次为单位，分位数不与基线单条分位数直接比较；摊销时间仅表示累计执行时间除以收到消息数，不是单条延迟。

以下两轮数据在最终共享 tag 防护加入前采集；实测发布器均逐条发送，未出现共享 tag。最终额外增加 tag 集合检查并删除无效的拆包关闭设置，完成测试回归，未重复两轮压测；数据反映该批量事务方案在本次实验镜像中的表现。

消费样本从第一批开始到最后一批完成的跨度为 **12.431 / 10.924 s**，最后一次 ACK 调用结束距突发开始 **12.589 / 11.054 s**。管理 API 仍在约 15 s 的快照中报告 100 条 unacked，直到 17.569 / 16.306 s 才满足连续空采样条件。管理统计存在滞后，所以采样排空时间包含统计刷新与探针间隔，不能全归为业务处理耗时；ready 峰值小也不证明队列从未积压。

### 消费分段

请求结束后才进入监听方法的批次，排除了突发期间显著的池争用。下表单位为 **ms/批次均值**，不是单条消息延迟：

| 阶段 | 混合（31 批 / 2993 条） | 匿名（38 批 / 3709 条） |
| --- | ---: | ---: |
| event 批量查询 | 1.789 | 1.301 |
| 完整 applyBatch 事务调用 | 11.476 | 7.786 |
| ↳ 批量防重 INSERT | 3.819 | 2.985 |
| ↳ 按文章统计 UPSERT | 1.290 | 0.518 |
| ↳ 提交近似段 | 5.834 | 4.023 |
| 每篇文章一次缓存删除 | 0.910 | 0.710 |
| 逐条 ACK 累计 | 5.281 | 4.079 |
| 整批消费执行 | **20.016** | **14.147** |
| 整批消费执行 p95 | 41.439 | 26.433 |
| 整批提交近似段 p95 | 5.863 | 6.078 |

SQL、提交和借连接是完整事务调用的子段，不能重复相加。该阶段 event/apply 借连接累计仅 **0.061 / 0.024 ms**（混合）与 **0.058 / 0.018 ms**（匿名）。总执行时间摊销到收到消息为 **0.207 / 0.145 ms/条**，这是成本摊销，不是事件端到端延迟或单条 p95；批次之间还等待发布器供给。

提交单次并未降为微秒：仍约 4–6 ms/批。收益主要来自次数下降，并同时减少数据库往返、统计重算与 Redis 删除次数。本测试所有事件集中在同一篇热点文章，因此每批只更新一篇文章；分散到很多文章时，统计 SQL 和缓存删除次数增加，需要另做分布负载验证。

### 连接与积压时间轴

下表分别列出最近快照中的 outbox / ready / unacked / Hikari 待连接；管理统计与数据库探针采集时间并非完全相同。

| 距突发开始约 | 混合 | 匿名 |
| --- | ---: | ---: |
| 5 s | 1351 / 0 / 0 / 73 | 2360 / 0 / 0 / 73 |
| 10 s | 3176 / 0 / 6 / 10 | 1009 / 74 / 100 / 0 |
| 15 s | 0 / 0 / 100 / 0 | 0 / 0 / 100 / 0 |

本轮消费调用中，event 与 apply 借连接累计合计 **3.818 / 3.322 s**，占消费累计执行约 **61.75% / 66.21%**，集中在 HTTP 突发期间。请求端 `dbAcquirePre/dbAcquireController` 平均 **28.01 / 39.97 ms**（混合），匿名 `dbAcquireController` 平均 **35.58 ms**。文章 lookup 平均 **25.58 / 28.21 ms** 含借连接，不能据此判定查询 SQL 本身慢。

发布器领取、发送、确认、标记每轮均为 10000 条、失败 0；累计 send **3.612 / 2.720 s**、claim **1.975 / 1.559 s**、mark **1.449 / 1.159 s**，批间平均空档约 **103.5 / 101.4 ms**，与 100 ms fixedDelay 一致。采到 `IO:WalSync`、`LWLock:WALWrite`，混合轮还采到 `LWLock:BufferContent`；未采到 Lock 等待，不能据此排除瞬时锁。

### 最终核对与低流量验证

两轮结束时，目标文章事实为浏览 **15000**、点赞关系 **5000**，统计为 **15000 / 5000**；processed **20000**，未发布 outbox **0**。文章和音乐工作队列、死信队列 ready/unacked 全部为 **0**，测试随机 schema 清理完毕。

另在 `learning-spring` 示例文章写入一条浏览事实及 outbox，验证不满批次时仍会处理：received/applied 均为 1，一次提交，统计 **1 / 0**；从 outbox 的创建时间到 ACK 调用结束 **174 ms**，监听方法内执行 **9.765 ms**。这是单次稀疏样本，包含发布轮询和聚批等待，不能当作保证上限。该样本单独保存在 `target/consumer-batch-sparse-*`，不纳入两轮汇总；此后全库 processed 为 **20001**，目标压测文章仍为 20000。

完成后仅停止 `air-perf-consumer-batch` 容器，独立卷保留。开发栈未重启或修改，以前实验卷未修改。

## 判断与下一步

逐条提交造成的持续几十秒消费积压已经明显缓解。当前这组负载主要暴露 HTTP 突发时共享连接池等待，以及 outbox 发布供给速度；消费者完成时间与发布器跨度接近。缓存删除和文章统计 SQL 目前占比很小，没有依据继续把文章内容查询列为主要瓶颈。

下一步先拆发布器 send 内的序列化/发送与 Confirm 回调，并在相同负载下比较有积压时连续处理多个有界批次与当前每批固定等待 100 ms 的策略。同步观察 HTTP 借连接、提交和 PostgreSQL 等待，避免仅增加连接池或消费线程。然后验证多文章分布与批大小 50/100 的多轮交替对照，检查公平性、稀疏延迟及未来多消费者的热点行锁争用。
