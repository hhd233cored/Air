# 2026-09-25 搜索关键词分布压测与缓存收益估算

## 目的和环境

判断搜索是否值得接入 Redis，特别是查询词大量不重复时的收益。使用独立 `air-perf` Compose 项目、4,000 条虚构已发布内容和原有 4 条参照内容；压测器与容器位于同一台 Windows 主机。Java 使用已完成 `V1002` trigram 优化的镜像。每档 45 秒，固定 `type=ALL&page=0&size=10`，请求完整读取响应正文。未修改开发库或真实音乐文件。

**当前搜索接口没有 Redis 缓存。** 下表的缓存命中率是假设每次 miss 立即写入、TTL 为 30 秒且容量无限时，按实际发出请求的键与时间估算的乐观上限；没有真实 Redis 命中数据，也没有包含锁等待、缓存序列化、写入和失效开销。压测后 Redis `DBSIZE` 仍为 0。

压测脚本与原始逐档结果分别在 [search-distribution.mjs](search-distribution.mjs) 和 [results-search-distribution-2026-09-25.jsonl](results-search-distribution-2026-09-25.jsonl)。

## 关键词分布

- **热门词**：`Spring` 与 `不存在的词` 各占约一半，只有 2 个不同键。
- **混合**：20% 为 `Spring`，40% 从 2,000 个存在的文章 ID 中取词，40% 为每次都不同的无匹配词。
- **几乎全新**：5% 为 `Spring`，95% 为每次都不同的无匹配词。

三种分布是为了测边界而设计的虚构负载，并非真实用户搜索比例。混合分布另测 600 RPS，用于观察更高流量。

## 结果

| 关键词分布 | 目标/实际 RPS | 请求数 | 不同键数 | 30 秒 TTL 理论命中上限 | p95 / p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 热门词 | 400 / 399.8 | 17,998 | 2 | 99.98% | 36.5 / 56.5 ms |
| 混合 | 400 / 399.7 | 17,997 | 9,199 | 42.22% | 28.8 / 34.6 ms |
| 几乎全新 | 400 / 399.7 | 17,992 | 17,093 | 4.99% | 19.6 / 28.0 ms |
| 混合 | 600 / 599.6 | 26,987 | 12,795 | 45.17% | 30.1 / 36.1 ms |

合计 80,974 次请求，全部 HTTP 200，没有网络错误或发压器丢弃。在 400 RPS 混合阶段，热门词、长尾 ID 词、唯一无匹配词各自的 p95 依次为 34.4、8.5、6.7 ms；600 RPS 混合阶段依次为 36.1、9.7、8.2 ms。选择性高或无匹配的查询已经较快，热门词仍是主要耗时来源。

只做了一次容器资源采样：400 RPS 热门词阶段 PostgreSQL CPU 约 373%，混合阶段约 178%，几乎全新阶段约 82%；该瞬时采样受时点影响，不能当作稳态 CPU 平均值。示例响应正文大小：`Spring` 3,730 字节、存在的文章 ID 词 4,193 字节、无匹配词 66 字节。全量缓存高基数查询会生成大量键，即使很多响应只有 66 字节，键名与 Redis 元数据仍占内存。

## 判断

现在没有证据表明需要为**所有**搜索请求增加 Redis：几乎全新词的理论命中上限只有约 5%，此类 SQL 已较快；在当前单实例虚构数据下，混合负载到 600 RPS 也没有出现尾延迟突增。对少量热门词做选择性缓存可能显著减少重复查库，但需先知道真实访问中的热门词占比。此前两个固定词的压测刻意制造了高重复率，不能代表真实命中率。

若以后接入，建议只缓存重复出现的第一页搜索，短 TTL、限制响应大小，并在内容事务提交后按版本号使旧搜索结果失效。当前 Redis 与登录 session 共用实例；不要让无限增长的搜索键挤占 session 内存。接入后再用相同三种关键词分布分别实测 Redis 命中率、PostgreSQL CPU、接口 p95 和 Redis 内存。

本项目目前没有真实搜索访问日志，所以本报告不能给出真实用户的关键词重复率或缓存命中预测；获取真实指标时应只记录规范化查询的哈希和聚合计数，避免保存原始用户搜索词。
