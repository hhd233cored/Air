# 文章指标有效写复测（2026-09-26）

## 环境与方法

使用当前源码构建 `air-perf-retest:local`，在新的 `air-perf-retest` Compose 项目和独立 PostgreSQL、Redis、RabbitMQ 数据卷中运行；原 `air-perf` 与开发库均未重置。Flyway V1004 已应用。加载 2000 篇虚构文章、5000 个虚构账号；限流关闭，阶段计时开启。同一 Node 客户端、100 个并发工作者，先让 5000 个账号各执行一次浏览、一次点赞，再执行 10000 次匿名有效浏览。混合场景每个工作者对同一账号先浏览再点赞。登录准备时间不计入突发吞吐。开发栈、客户端和压测栈共用本机资源，未固定资源配额。

脚本增加了混合场景中浏览和点赞各自的结果与阶段汇总。原始输出保存在 `target/retest-mixed-2026-09-26.jsonl` 和 `target/retest-anonymous-2026-09-26.jsonl`；不含密码或 Cookie。

## 阶段与等待

下表为每次请求的平均毫秒；`controller` 包含 `lookup` 和 `transaction`，各列不能相加。`lookup` 包含从 Hikari 获取连接的等待，不是 PostgreSQL 单条 SQL 耗时。

| 场景 | preController | lookup | transaction | controller | HTTP 未覆盖阶段 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 混合有效写 | 36.98 | 31.85 | 24.86 | 56.73 | 10.71 |
| 其中浏览 | 37.55 | 32.07 | 25.11 | 57.22 | 11.99 |
| 其中首次点赞 | 36.42 | 31.62 | 24.61 | 56.24 | 9.43 |
| 匿名有效浏览 | 1.39 | 35.77 | 17.31 | 53.08 | 18.95 |

混合场景事实 INSERT、outbox INSERT、近似 COMMIT 平均分别为 0.69、0.53、7.31 ms；匿名场景分别为 0.67、0.54、4.81 ms。混合与匿名的 Hikari 活跃连接采样最大均为 10，待连接线程最大分别为 84、80。PostgreSQL 活动等待采样见 `IO:WalSync`、`LWLock:WALWrite` 等；未采到 `Lock` 等待。探针与业务共用连接池，采样可能漏掉短暂峰值。

负载停止后的 `EXPLAIN (ANALYZE, BUFFERS)` 确认 `publishedArticleId` 的原查询使用 `content_items_public_normalized_slug_idx`，数据库执行时间为 0.076 ms。因此并发下约 32–36 ms 的 `lookup` 均值主要发生在 SQL 执行时间之外；连接池排队是直接观察到的候选来源。已登录请求的 `preController` 明显高于匿名请求，但它还包含 Session、账号查询的取连接等待、CSRF 等，不能全部命名为认证计算耗时。

## 异步收敛与最终核对

混合突发完成后，浏览计数在第 70 次每秒轮询达到 5000；随后首次读取点赞计数已是 5000，因此无法从该次轮询得出点赞的独立收敛时间。匿名突发后，浏览计数在第 75 次轮询达到 15000。轮询次数仅近似说明突发完成后还需约一分钟，不能当作单次 HTTP 延迟。

最终 PostgreSQL：浏览事实 15000、点赞关系 5000、已处理事件 20000、未发布 outbox 0、统计 15000/5000；RabbitMQ 文章工作队列和死信队列的 ready/unacked 均为 0。

20,000 个事件的数据库时间戳显示，LIKE 的 `created_at` 到 `published_at` 标记 p50/p95 为 42.48/66.55 s，到 `processed_at` 为 44.02/68.17 s；VIEW 分别为 39.53/71.38 s 与 40.13/71.35 s。VIEW 包含混合与匿名两轮。`published_at` 是发布确认后的数据库标记，不是 RabbitMQ 实际收到消息的时间；有 5315 个 VIEW 在该标记前已处理。现有数据能确认异步管线存在数十秒积压，但还不能单凭这两个时间戳将积压精确归因于发布器、消费者或它们竞争数据库连接。

## 判断与下一步

新索引已解决空闲时的文章 slug 顺序扫描。有效写当前可直接观察到的限制是 Hikari 连接池排队；它影响文章查询调用，也可能影响认证中的账号核对。HTTP 接收完成后的读模型收敛另有明显积压。下一步先对连接获取时间、outbox 待发布数、RabbitMQ 队列深度和消费速率做同一时间轴采样，再分别测试连接池容量和 outbox 批量标记／消费者吞吐；不要把连接池调大或引入 Redis Lua 当作未经验证的修复。
