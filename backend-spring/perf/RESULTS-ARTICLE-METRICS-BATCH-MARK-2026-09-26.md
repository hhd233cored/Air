# 文章指标批量发布标记：实现与复测（2026-09-26）

## 改动

新增内部仓储接口 `markPublishedBatch(List<UUID>)`，替换发布器的逐条标记调用。每批最多 200 条事件，处理流程为：

1. 在原有短事务中领取事件，租约仍为 30 秒。
2. 发送持久化消息，逐条核对 Confirm；只有 ACK 且没有 Return 的 ID 才进入成功集合。
3. 确认检查结束后，用**一条 UPDATE、一个短事务**标记成功集合。更新条件保留 `published_at IS NULL`，清除成功行的租约，返回实际更新行数；空列表返回 0。

等待 RabbitMQ 确认时不持有数据库事务。发送异常、NACK、Return 或确认异常仍单独延期重试。批量标记失败会记录错误并保留事件，由原租约到期后重新领取；即使数据库提交结果不确定，消费者的事件唯一键也保证重复投递不重复计数。延期操作本身失败时也保留原租约，并继续处理其他事件。

此改动在默认配置下生效，不依赖压测开关；没有修改消费者逻辑、队列容量、调度间隔或数据库结构。计时开关仍默认关闭。开启时增加 `markMode=batch`、`markRequested`、`markCalls` 和 `markBatch`，区分批量调用耗时与按事件摊销的时间；汇总脚本兼容旧的逐条标记记录。

代码：[仓储批量接口](../src/main/java/org/airchord/backend/metrics/ArticleMetricRepository.java)、[发布器](../src/main/java/org/airchord/backend/metrics/ArticleMetricOutboxPublisher.java)、[计时](../src/main/java/org/airchord/backend/metrics/ArticleMetricPublisherTiming.java)。

## 可靠性验证

在 Java 21 Linux 构建容器中运行指定的发布器和文章指标测试，共 **10 项通过，失败/错误/跳过均为 0**：

- 计时开启和关闭两种配置均验证：只批量标记 ACK 且没有 Return 的事件；失败事件进入延期流程。
- 等待未完成确认时，批量标记尚未开始。
- 批量标记异常保留原租约，不退回逐条标记；某条延期异常不会阻止其他成功事件被标记。
- PostgreSQL 集成测试使用随机独立 schema 和 Spring 事务代理，验证子集更新、重复标记、空集合，以及一行约束失败时整条 UPDATE 回滚。
- 模拟租约到期后可重新领取；重复消费不会重复计数。原有并发点赞与浏览幂等测试也通过。

测试结束后随机 schema 已全部清理。日志见 [测试记录](../target/batch-tests-2026-09-26.log)。本机 Windows Maven 的测试编译仍出现此前的主类查找问题；本轮通过 Linux 容器完成了实际编译与测试，没有修复该环境问题，也没有声称全量测试套件通过。

## 复测方法

新建隔离 Compose 项目 `air-perf-batch`，专用镜像 `air-perf-batch:local`，应用本机端口 18087、RabbitMQ 管理端口 18088。独立数据库和消息卷，V1004 已应用，加载相同的 2000 篇虚构文章、5000 个虚构账号。关闭限流，100 个客户端工作者，开启相同的请求阶段、等待时间轴与发布器计时。

先运行 5000 次有效浏览加 5000 次首次点赞，完全排空后再运行 10000 次匿名有效浏览。两轮均 **10000 次 changed**，所有事件领取、发送、确认、标记均成功，失败为 0。对照来自 [上一轮逐条标记拆测](RESULTS-ARTICLE-METRICS-PUBLISHER-2026-09-26.md)，使用相同负载和脚本。构建及可靠性测试已在发压前结束。

## 发布器结果

| 指标 | 混合：逐条 → 批量 | 匿名：逐条 → 批量 |
| --- | ---: | ---: |
| 数据库标记调用数 | 10000 → **51** | 10000 → **52** |
| 标记累计耗时（含借连接和提交） | 83.754 → **0.830 s** | 83.991 → **2.470 s** |
| 标记占批次执行时间比例 | 96.17% → 16.49% | 97.05% → 32.55% |
| 完整 200 条批次标记 p50 | 1571.427 → **11.320 ms** | 1592.516 → **42.720 ms** |
| 完整 200 条批次标记 p95 | 1892.353 → 45.467 ms | 2024.233 → 166.603 ms |
| 第一批开始至最后一批结束 | 92.264 → **10.148 s** | 91.837 → **12.765 s** |
| 发布器执行时间合计（不含批次间隙） | 87.091 → 5.034 s | 86.542 → 7.589 s |

标记累计耗时分别减少约 **99.0% / 97.1%**，说明之前的逐条数据库调用与提交是有效优化点。分位数指每批 200 条的标记合计，不是单条事件延迟。按事件摊销的标记时间分别为 0.083 / 0.247 ms，也不能当作每条事件独立延迟。

仅看 HTTP 突发结束后才开始的批次，200 条标记 p50 为 **7.006 / 10.556 ms**，对应此前 **1551.648 / 1584.104 ms**。这些批次的标记借连接累计仅 0.015 / 0.022 ms。匿名全轮标记借连接累计仍有 1.858 s，主要集中于突发或跨界批次，因此其全轮标记分位数高于混合轮。

批量版本的单条异步确认延迟均值为 3.832 / 4.084 ms，实际确认等待累计为 0.163 / 0.188 s。它比旧轮的累计阻塞等待略高，是因为现在连续检查整批确认，少了逐条数据库标记期间供后续确认完成的时间；确认延迟仍与发送等工作重叠，不能把它累加到批次串行耗时中。

匿名轮请求结束后有一个领取调用达到约 427 ms，拉高该组 p95；等待采样也观察到 WAL 和 Vacuum 相关等待。本轮没有进一步拆解该离群值，不能据此断言领取 SQL 是新的整体瓶颈。

## 后续建议与限制

下一步应拆测消费者的 `event` 查询、`apply` 事务、提交和 Redis 缓存失效；其中点赞 `apply` 每次从关系表重算数量，浏览则更新同一文章统计行。先确定各段耗时，再考虑合并同批事件、批量幂等落库或调整消费并发；热点行上的并发更新可能引入锁等待，增加消费者数量并不保证加速。本轮没有修改消费端。

这是一台主机上的先后单次试跑，开发栈仍运行，探针与日志有开销，没有随机顺序、多轮统计或固定机器资源。因此数字描述本次实际结果，不能直接作为线上容量或严格收益倍数。匿名轮在混合轮之后使用同一隔离数据库，与旧轮顺序一致。
