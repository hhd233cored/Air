# 发布器发送拆测、有界连续发布与多文章对照（2026-09-26）

## 实现与测量口径

本次接续 [批量消费者记录](RESULTS-ARTICLE-METRICS-CONSUMER-BATCH-2026-09-26.md) 的后续计划。消费者包括最终的共享 deliveryTag 防护，本次所有组使用同一 Java 21 镜像，数据库池与消费者并发未扩大。

发布器仍每批 claim 200 条，分别核对每条 Confirm 与 Return，再一次批量 mark。满 200 条且发送、确认、标记均成功时可立即处理下一批；不足一批、任一失败、达到次数上限或下一批准入预算时结束，等待原有的 100 ms fixedDelay。

- `ARTICLE_METRIC_PUBLISHER_MAX_BATCHES`：默认 1、范围 1–10，实验比较 1 与 4。匿名 HTTP 未显示稳定收益，连续发布保持为可配置候选。
- `ARTICLE_METRIC_PUBLISHER_RUN_BUDGET_MS`：1–1000 ms，实验为 250 ms。预算从本轮开始计算，只用于判断是否再领一批；不强行中断已领取事件，所以不是整轮完成时间的硬上限。
- 同一批所有 future 共享发送结束后的 5 秒确认等待窗口，避免每个未完成 future 各等 5 秒。失败仍 defer，标记事务失败仍保留原租约，consumer 唯一键处理重投；确认超时不删除事实与 outbox。

新增发送嵌套字段：

| 字段 | 测量范围 |
| --- | --- |
| prepareMs | CorrelationData、观察 future 注册与 JSON 字符串准备 |
| payloadMs | JSON 字符串准备，是 prepare 子段 |
| templateMs | 完整 convertAndSend 调用 |
| convertMs | 进入 template 调用到 MessagePostProcessor 入口，包含转换与入口开销 |
| propertiesMs | PostProcessor 设置持久化与 messageId |
| rabbitAfterConvertMs | template 减去转换与属性设置的剩余；包含通道取得、Confirm 注册、客户端发送等，不等于纯网络或 broker 执行时间 |
| confirmLatencyPerEvent | 从发送准备开始到 future 完成观察回调入口，含 broker、网络与回调调度 |
| confirmAfterSendReturnPerEvent | 从 template 返回到观察回调的非负间隔；先于返回的确认单独计数 |
| confirmWaitMs | 发布线程实际等待 future 的时间，与上述异步延迟含义不同 |

这些嵌套字段不能与 sendMs 再次累加。观察回调只记录完成时间，没有将其几行计时代码的执行耗时冒充完整 Spring 回调耗时。仍不能从这些字段单独区分 RabbitMQ 持久化、网络 RTT 与 Spring 回调队列。

日志增加 turnId/batchIndex/maxBatchesPerRun，汇总区分轮内与轮间空档。完整批次 p95 是 200 条批次的分位数；每批单事件确认 p95 不能合并为全体事件 p95。历史日志缺少的新字段报告 null。

## 验证与环境

39 个测试全部通过：消费者 18、发布器 18、PostgreSQL 集成 3，无跳过。新增测试覆盖满批继续且受次数上限约束、短批不忙轮询、批量 mark 失败停止下一次 claim、慢批次触发预算，以及三个未完成 future 共用约 5 秒窗口。原 ACK/NACK/Return/发送异常、租约重试、防重、事务回滚与缓存失效验证继续通过。

测试日志：`target/publisher-drain-tests-2026-09-26.log`。最终将默认最大批次数保持为 1 后重新构建，并再次通过全部 39 个测试，日志为 `target/publisher-drain-tests-final-2026-09-26.log`；最终镜像单独命名 `air-perf-publisher-drain-final:local`，保留测量镜像。

实验构建使用此前 Java 21 构建镜像的相同 Maven 依赖缓存，离线编译当前 src/pom；运行镜像保留相同 JRE 与 JVM 参数，所有对照共享镜像 `air-perf-publisher-drain:local`，ID 为 `sha256:f725bdb1118e5dffc3ff60f86b37e919fb12e7f428ad88017f03f216cca714ca`。每轮明确配置最大批次数 1 或 4，因此最终默认值调整不影响测量数据。实验 Dockerfile 与构建日志在 `target/publisher-drain*`，常规 Dockerfile 未修改。

独立项目分别为 `air-perf-drain-control`（18101/18102）、`air-perf-drain-candidate`（18111/18112）、`air-perf-drain-spread`（18121/18122）。仅一组实验栈在测量时运行，开发栈继续运行；以前的数据库卷未修改。夹具均为 2000 篇虚构文章与 5000 用户。

每轮 10000 次有效写、固定并发 100、限流关闭，HTTP/发布/消费采样开启，并每约 500 ms 记录取连接、outbox、队列与 PostgreSQL 等待。准备登录不计入 RPS。单文章发布对照各含 mixed 与 anonymous-view；匿名轮在混合轮完全排空后运行。

多文章组采用 100 篇文章 round-robin，5000 用户每人一次浏览加一次点赞，每篇预期浏览/点赞均为 50。不同轮使用不同文章范围，保留每轮事实，无清库。消费者 50/100 采用 AB、BA、AB 顺序（50、100、100、50、50、100），每种三轮；发布器保持最大 4 批与 250 ms 预算。脚本逐篇等待预期计数，并在 DB 核对事实、统计、processed 与 outbox，还输出各文章 HTTP 延迟与完成时间摘要。

## 实测结果

### 单文章：每轮 1 批与最多连续 4 批

各轮 10000 次请求全部 changed，发送、确认、发布标记与首次消费全部为 10000，失败、重投、缓存删除失败均为 0。最终每组数据库浏览事实 15000、点赞关系 5000，统计 15000 / 5000，processed 20000、unpublished 0，工作与死信队列全空。

| 指标 | 混合：1 批 → 最多 4 批 | 匿名：1 批 → 最多 4 批 |
| --- | ---: | ---: |
| HTTP RPS | 987.4 → 1055.3 | 1070.0 → 984.8 |
| HTTP p95 | 179.3 → 150.5 ms | 186.7 → 211.9 ms |
| 发布器跨度 | **11.498 → 9.509 s** | **12.158 → 11.267 s** |
| 最后一批 ACK 调用结束距突发开始 | **11.712 → 9.681 s** | **12.323 → 11.416 s** |
| 管理采样连续为空距突发开始 | 12.463 → 13.034 s | 13.149 → 14.960 s |
| 发布批次 / 调度轮数 | 51 / 51 → 57 / 38 | 52 / 52 → 52 / 28 |
| 轮内批间平均空档 | 无 → 1.421 ms | 无 → 0.875 ms |
| 轮间批次平均空档 | 103.480 → 102.027 ms | 102.627 → 108.815 ms |
| HTTP 取连接：认证前段均值 | 23.28 → 8.38 ms | 0 → 0 ms |
| HTTP 取连接：controller 内均值 | 35.57 → 12.54 ms | 60.93 → 70.34 ms |
| HTTP 提交近似段均值 | 7.07 → 5.29 ms | 7.02 → 7.68 ms |
| outbox 待发布采样峰值 | 1820 → 595 | 3285 → 2735 |
| RabbitMQ ready 采样峰值 | 0 → 119 | 89 → 200 |

连续发布确实减少了等待固定轮询的空档，混合发布跨度缩短约 17.3%、匿名约 7.3%。不足满批或预算用完仍会结束，因此“最多 4 批”不代表每轮总能发 800 条。

匿名轮 HTTP RPS 下降约 8%，p95 与取连接均值上升，同时单次提交均值也上升。仅一组先后对照不能区分策略影响与同机 I/O、JIT、调度等变化，也不足以认定入口吞吐稳定改善。因此默认继续每轮 1 批，有明确积压时可配置 4，并用自己的负载验证。

管理采样排空时间在连续组反而较晚，但消费者 ACK 时间较早：管理统计刷新与探针间隔影响该指标，不能用管理采样时间单独否定或量化处理改善。mixed 的请求耗时中“已测 servlet 阶段以外”均值仍达 63.41 ms（基线 30.25 ms），还包含客户端、网络及请求调度；取连接下降不等于全部请求等待消失。

### 发送内部拆测

| 累计耗时（s） | 混合 1 批 | 混合最多 4 批 |
| --- | ---: | ---: |
| 总 send | 2.971 | 3.520 |
| prepare（含 payload） | 0.076 | 0.093 |
| ↳ payload 字符串准备 | 0.052 | 0.067 |
| template | 2.885 | 3.416 |
| ↳ 转换与入口段 | 0.052 | 0.060 |
| ↳ 属性设置 | 0.003 | 0.003 |
| ↳ 转换后的客户端发送剩余段 | **2.830** | **3.352** |
| 发布线程实际等待 Confirm | 0.157 | 0.220 |

每轮 10000 次消息转换均采到。Confirm 完成观察延迟均值 **3.616 / 4.342 ms**；从 template 返回到观察回调的非负均值 **3.320 / 3.991 ms**，先于返回完成的事件 **2 / 3** 条。确认延迟主要与发送其他消息重叠，所以不能把 10000 × 确认均值再加到串行发布耗时。

主要 send 成本在消息转换之后的客户端调用，JSON 字符串与转换不是这组小载荷的主要成本。剩余段仍包含通道取得、Confirm 注册与客户端写入等，暂不能归因成某一种纯 broker 或网络耗时。

批大小 100 将提交次数约减半，但按文章分组的收益有限：缓存删除次数减少约 14.7%，消费累计执行减少约 7.6%，最后 ACK 时间减少约 7.9%。同时聚合 HTTP RPS 低约 3.9%，三轮 p95 均高于 50 组。100 有助于降低读模型处理成本，50 在本次入口请求延迟上更好；这不是普遍优劣结论。继续保留既有消费者默认 100，本次没有修改消费者配置默认值。这六轮是在发布器最大 4 批下测得，不能直接当作默认发布器 1 批下的 50/100 对照。

| R1 | 59.12 | 6.93 | 353 | 5630 | 82 | 16.236 | 72.1 |
| R2 | 71.47 | 7.21 | 827 | 4532 | 76 | 17.127 | 214.4 |
| R3 | 64.17 | 7.05 | 346 | 3998 | 82 | 18.199 | 75.4 |

ready 有数千条积压，最后 ACK 约为 13–15 秒，发布供给完成约为 10–11 秒；相比单篇负载，消费者逐篇处理成本成为更明显的限制。HTTP 突发期间仍有共享池等待，因此整个系统同时存在入口等待与异步消费成本，不能把一个阶段称为所有场景唯一瓶颈。

六轮都未采到 `Lock` 等待；采到 `IO:WalSync`、`LWLock:WALWrite`，部分轮还包括 `IO:WalInitWrite`、`IO:WalWrite`、`IO:DataFileExtend`、`Timeout:VacuumDelay`。这不排除瞬时锁，也不证明扩大并发安全。R2 消费提交近似段最大 327.583 ms，p50 为 5.431 ms、p95 为 9.207 ms，少数 I/O/调度长尾会显著影响均值。

每篇文章都有 100 次 HTTP 请求、50 次浏览和 50 次点赞，没有遗漏文章。各文章 HTTP p95 范围分别为 R1 141.7–208.1、R2 158.3–249.7、R3 152.1–232.2、R4 118.9–186.2、R5 135.8–224.4、R6 159.9–248.2 ms。以上是 HTTP 请求分布与完成时间检查，尚未记录每篇文章全部事件的提交时间分布，不能据此保证 RabbitMQ 调度公平性。

### 稀疏延迟与最终数据核对

每种批大小另发一次单条匿名浏览，使用未用过的文章 1501/1502。等待参数仍为 100 ms，发布器最大 4 批：

| 指标 | 批大小 50 | 批大小 100 |
| --- | ---: | ---: |
| HTTP 耗时 | 12.9 ms | 12.9 ms |
| outbox 创建至 ACK 调用结束 | 191 ms | 129 ms |
| 消费监听方法内执行 | 7.955 ms | 7.520 ms |
| 接收 / 首次处理 / 提交 | 1 / 1 / 1 | 1 / 1 / 1 |

创建时间取实验数据库 outbox 的 `created_at`，终点为消费日志 `endedAtEpochMs`；时间包含发布轮询与监听方法进入前的聚批等待。每组只有一个样本，不能作为 SLA 或证明 100 比 50 更低延迟。

六轮每轮逐篇核对均为 wrongArticles 0，outbox/processed 各 10000，unpublished 0。加上两条稀疏请求，全库浏览事实及统计均为 **30002**，点赞关系及统计均为 **30000**，outbox/processed 均为 **60002**，未发布 **0**，测试 schema 残留 **0**。队列核对工作/死信队列均为空。最终核对文件为 `target/spread-final-validation-2026-09-26.json`。

## 判断与后续计划

1. **发布器**：连续批次消除了满批之间约 100 ms 的固定空档，能缩短发布跨度；入口 HTTP 没有稳定收益，默认最大批次保留 1，4 作为有积压时的候选。小事件载荷的 JSON 准备与转换并非主要发送成本。
2. **多文章消费者**：优先把每篇一次 Redis `delete` 改为每批收集唯一键、一次批量删除，并保留提交后失效、失败可观察的语义。之后把逐篇统计 UPSERT 合成一次按文章分组的 SQL，核对点赞关系事实、防重、重投、回滚与缓存处理；再复测 100 篇负载。这两项减少网络往返，依据比继续扩大连接池或消费线程更直接。
3. **未来多消费者**：本次仍为单消费者，未实施并发扩容或热点行锁实验。扩大并发前先验证多事务同时计算点赞关系与统计 UPSERT 的一致性，再测试单篇热点和分散文章，观察行锁与每篇事件提交延迟。

本次同机运行、资源未做独占或固定配额，数据库随轮次增长；50/100 采用交替顺序，每种均有两次应用启动后的轮次与一次不重启的轮次，但没有严格随机化或统计置信区间。不能将这些数字外推为生产容量，也不能把一次组间差异完全归因于参数。事实正确性逐轮核对通过，性能结论保留上述边界。

## 复现

使用 [run-metric-experiment.ps1](run-metric-experiment.ps1) 启动、运行、汇总和核对。先按 perf README 准备 `target/perf.env` 与夹具目录；新环境可用常规 Dockerfile 构建 `docker build -t air-perf-publisher-drain:local .`，此命令构建当前源码，ID 会与本次历史测量不同。一轮对应一个唯一 Label，拒绝覆盖已有结果。Seed 仅允许尚无压测夹具的新实验库；脚本没有删除数据库或卷的操作。例：

```powershell
./perf/run-metric-experiment.ps1 -Project air-perf-drain-example-20260926 `
  -Label spread-example-b50 -AppPort 18131 -RabbitPort 18132 `
  -PublisherBatches 4 -ConsumerBatchSize 50 -ArticleCount 100 -ArticleOffset 1 -Seed
```

再次运行用新的 Label 与未使用的 ArticleOffset，并省略 Seed；最后一轮加 StopStack，只停止该项目，保留卷。脚本从 ignored 的 `target/perf.env` 读取虚构用户和 MQ 凭据，不输出密码。

每个 Label 保存请求与时间轴 `.jsonl`、发布与消费原始日志和汇总、`-validation.json` 与 `-queues.txt`，均在 ignored 的 `target/`。`PERF_ARTICLE_COUNT/PERF_ARTICLE_OFFSET` 也可直接用于 `article-metrics-compare.mjs`，默认仍是一篇文章。

本次 Label 为 `drain-{control,candidate}-{mixed,anonymous}-2026-09-26`、`spread-r1-b50`、`spread-r2-b100`、`spread-r3-b100`、`spread-r4-b50`、`spread-r5-b50`、`spread-r6-b100`、`spread-sparse-b50`、`spread-sparse-b100`（spread 均追加 `-2026-09-26`）。跨轮汇总为 `target/drain-experiments-summary-2026-09-26.jsonl` 与 `target/spread-experiments-summary-2026-09-26.jsonl`，入口为 [summarize-metric-experiments.mjs](summarize-metric-experiments.mjs)。
