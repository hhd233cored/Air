# 2026-09-25 本机首轮压测记录

## 环境与方法

- 独立 `air-perf` Compose 项目，使用与开发服务相同的 Java 镜像，但 PostgreSQL、Redis、RabbitMQ、账号、音频目录和持久化卷均独立；开发服务与真实音乐文件未参与压测。
- 虚构数据：2,000 篇已发布文章、2,000 条已发布说说、10,000 条评论、1,000 条留言，外加原有少量参照记录。
- Node.js 24.15.0 从同一台 Windows 主机按目标请求/秒发压；每级 30 秒。`results-2026-09-25.jsonl` 保留原始阶段统计。响应时间包含本机 HTTP 往返和完整响应正文读取。
- 默认限流、20 个未完成音频任务上限和 1 GiB 暂存上限均保持原值。

## 主要结果

| 场景 | 目标/实际请求每秒 | 请求数 | p95 / p99 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 公开读取混合，100 档 | 100 / 99.9 | 2,997 | 12.1 / 14.3 ms | 全部 200 |
| 公开读取混合，800 档 | 800 / 799.1 | 23,981 | 12.9 / 24.2 ms | 全部 200，无压测器丢弃 |
| 搜索，200 档 | 200 / 199.5 | 5,998 | 84.3 / 96.3 ms | 全部 200 |
| 搜索，240 档 | 240 / 238.4 | 7,196 | 178.1 / 269.5 ms | 全部 200，尾延迟开始上升 |
| 搜索，320 档 | 320 / 228.9 | 7,044 | 1,916.9 / 2,697.2 ms | 全部 200，但压测器因 200 个并发上限跳过 2,553 个计划请求 |
| 已登录 `/auth/me`，60 档 | 60 / 59.9 | 1,798 | 11.6 / 13.1 ms | 全部 200 |
| 混合持续 3 分钟，200 档 | 200 / 199.9 | 35,999 | 70 / 92 ms | 全部 200，无压测器丢弃 |

混合持续测试的请求比例为公开读取 60%、搜索 25%、已登录账号读取 15%。所有阶段合计记录 136,258 次请求，没有网络错误或 5xx。公开读取只测到 800 请求/秒，不能据此推断更高负载的上限。

搜索曾有一次目标 160 请求/秒时 p95 达 1,474.5 ms、实际 153 请求/秒的尖峰。随后同档重复两次，实际均约 159.7 请求/秒，p95 分别为 83.5 和 85.5 ms。因此这次尖峰不作为稳定容量结论。更高档位的 240、320 请求/秒展示了明显的延迟增长和吞吐停滞。

25 个约 1 MiB 的虚构 WAV 同时提交：20 个收到 `202`，5 个收到容量 `503`；接受的 20 个任务约 4.7 秒内全部变为 `SUCCEEDED`，歌单恰好增加 20 首，outbox 无待发布事件，工作队列和死信队列均为空。提交响应 p95 为 582.4 ms。默认限流检查中，连续登录的 7 次请求为 5 个 `200`、2 个 `429`；同一账号连续评论 12 次为 10 个 `201`、2 个 `429`。

## 资源与发现

- 公开读取 800 请求/秒时的一次采样：Java 约 623 MiB、PostgreSQL 约 90 MiB；CPU 分别约 114% 和 171%（Docker 的 100% 表示约一个逻辑 CPU）。
- 混合测试中 Java 内存采样约 873 MiB，结束后空闲采样约 844 MiB。短时 JVM 内存保留不能说明内存泄漏，需要更长时间测试和堆指标才能判断。
- 高负载搜索时 PostgreSQL CPU 采样接近 10 个逻辑 CPU。隔离库的 `EXPLAIN (ANALYZE, BUFFERS)` 显示，无匹配关键词的 `COUNT(*)` 使用 `Seq Scan`，扫描 4,004 行约 31 ms；当前全文匹配与字面 `POSITION` 匹配的 `OR` 条件使这类查询走全表扫描。搜索是下一步最值得剖析的路径。
- RabbitMQ 在压测结束时没有积压。个别 CPU 瞬时采样受到 RabbitMQ 管理命令和健康检查干扰，没有将其用于容量结论。

## 结论的适用范围

这是同一台主机上的短时单实例测试，测试数据比真实长期运行的数据简单，压测器也与 Docker Desktop 争用主机资源。它可用于比较当前接口和发现搜索尾延迟，但不能直接作为线上并发承诺。下一轮可用独立发压机、生产规模的虚构数据、按接口分别统计延迟，并延长稳定负载测试。
