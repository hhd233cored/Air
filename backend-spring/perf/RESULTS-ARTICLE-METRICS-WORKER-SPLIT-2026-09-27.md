# 四进程发压与固定总连接预算的池隔离实验

日期：2026-09-27。继续[独立采样与长测记录](RESULTS-ARTICLE-METRICS-OBSERVER-LONG-2026-09-27.md)的后续工作：减小单进程发压调度负担，再对照统一20连接与HTTP16/文章后台4连接。完成6轮120秒对照和2轮300秒长测。

## 结论

1. **四进程改善了实际发压稳定性，但增加了发压CPU成本。** 120秒重复轮次的加权吞吐从922.9提高到980.2 RPS，漏发从7.61%降到1.92%；负载worker CPU从约1.10核升到2.51核。单进程两轮漏发全部是迟到，四进程仍有迟到和并发满漏发，不能据此确认无漏发的1000 RPS容量。
2. **16+4隔离确实保护了文章后台取连接，但整体收益不足以定为默认方案。** 长测吞吐982.7→987.8 RPS、HTTP p95 123.3→114.1 ms，HTTP p99 239.7→243.1 ms；消费apply起点滞后p95反而3.19→13.37秒，outbox峰值3,677→15,231。后台实际最多2个连接活跃、没有pending样本，HTTP池平均取连接总耗时5.96→8.98 ms。还存在实验顺序与数据库历史量的混杂，不能将滞后恶化直接归因于拆池。
3. **入口主要成本仍是提交与连接竞争，新增需要定位的是发布器批量标记慢段。** 账号/文章SQL全轮平均0.54–0.77 ms，HTTP提交8.03–10.56 ms，占连接持有68%–74%。拆池长测第10–80秒，批量`markPublishedBatch`平均56–84 ms，后台取连接约0.002 ms；第80秒后标记回落至约17–20 ms并逐步追平积压。下一步应拆出标记的SQL与提交，记录执行计划/扫描行数，再用一致数据库快照做对照。

正式负载共**1,285,896次changed写入**，全部发布、消费、逐篇计数一致，无重试和业务失败。以下列出完整口径与依据。

## 实现与统计口径

- `LoadWorkers=1/4`。4个独立Node进程分担目标速率和并发预算，约定同一墙钟起点，用不同phase交错请求，避免4个进程同时批量发送。混合请求仍是浏览完成后点赞，每个进程处理全局index的固定余数，用户/文章组合不重复。每进程并发上限50，总上限200；静态分配不能把空闲槽位实时借给另一个worker，可能影响并发满漏发。
- Cookie与CSRF只通过私有IPC传递。请求计时在各worker采集，全量请求样本在负载结束后回传，按共同时间轴合并。HTTP分位数从全部实际请求重新计算，调度lateness从全部已发送单位重新计算，不平均worker分位数。
- CPU时间为worker合计，事件循环利用率为worker均值；事件循环p99列是**各worker p99的最大值**，另保留每进程数值，不是全局p99。协调进程另有`coordinator-runtime`记录；burst边界与HTTP吞吐使用worker负载完成时刻，排除结束后IPC回传和汇总开销。并发峰值合并为各worker最大值之和，是上界。
- `BackgroundPoolSize=0/4`只在perf计时配置启用时生效。4表示从既定20预算划出4连接供文章发布/消费使用，HTTP保留16；两池minimum-idle与maximum相等，探针核对实际16+4并分别采样。普通产品配置没有启用这一实验开关。
- 路由作用域在发布/消费事务开始前设置，结束或失败后恢复。Spring绑定在同一个逻辑DataSource上的事务连接保持一致；入口事实/outbox、消费者processed/stats仍各自原子提交。没有给入口每条SQL另建事务，也没有增加数据库连接总额。后台Hikari配置沿用原连接配置（[HikariCP 7.0.2源码](https://github.com/brettwooldridge/HikariCP/blob/HikariCP-7.0.2/src/main/java/com/zaxxer/hikari/HikariConfig.java)）。
- 新隔离项目`air-perf-drain-split-20260927`，app18701、Rabbit18702，开发栈继续运行，所有旧实验卷保留。应用统一镜像`air-perf-split:local`，JRE与上轮一致。本轮不将旧镜像的测量直接作为改造收益。
- 应用镜像ID为`sha256:8602f2dcdf27fef3317da4d978b783dae291a8e393524f5abc6b916964d072a5`；客户端统一`node:24.15.0-alpine`，ID为`sha256:d1b3b4da11eefd5941e7f0b9cf17783fc99d9c6fc34884a665f40a06dbdfc94f`。Docker可见32 CPU、内存8,164,098,048 bytes（约7.60 GiB）。资源记录在`target/worker-split-daemon-resources-2026-09-27.txt`。
- 所有正式轮次都是Linux容器客户端、混合写入、100篇文章、目标1000 HTTP/s、总并发200、JDBC10%抽样、独立探针、JFR/GC与PG/WAL区间采集；发布4批×200、run budget250 ms，消费100/100 ms。fsync/synchronous_commit开启，压测限流关闭。
- 顺序：120秒 **1worker统一 / 4worker统一 / 4worker拆池 / 4worker拆池 / 4worker统一 / 1worker统一**，再分别对4worker统一与拆池做300秒负载。每轮重启应用、登录准备不计入窗口，使用新的100篇文章范围1–800，共享本轮实验卷并保留历史。
- 两轮长测开始前，实验outbox分别已有693,916、989,574条历史事件。新文章消除了组合重复，但历史表大小、死元组、统计信息与自动维护状态没有恢复到相同快照。短测重复轮次采用回返顺序，长测每配置仅1轮，不能把约0.5%的吞吐差当成已确认收益。
- “HTTP池”实际是主池，也承接未进入文章后台作用域的任务，例如音乐导入定时发布器。JFR分别列HTTP线程、非HTTP线程、调用栈可识别的文章后台Hikari等待；非HTTP等待不能全部归为文章后台池。JFR等待是多线程累计值，可超过墙钟时间；事件阈值与截断调用栈限制了覆盖范围。
- 仍共用本机和WSL资源。进程数、并发静态分配、独立Undici连接管理等同时变化；本轮不能把收益只归因于一个原因，也不能据此确定专用服务器容量上限。

## 验证

- 文章指标相关Java **59项通过，无跳过**。新增验证：作用域在嵌套/异常后恢复、总预算20保持16+4、默认统一池，以及真实PG上的入口回滚、消费回滚/重试/防重、已绑定事务的连接保持同一PID。
- Node **11项通过**：包括协同phase覆盖全局到达序列、组合唯一性、原始lateness合并、丢失到达拒绝、独立探针与传输关联。假时钟测试在sleep推进前让任务微任务执行，与真实timer顺序一致。
- 测试镜像首次offline回归因缺少Surefire运行器依赖退出；补齐依赖后59项完整执行成功。业务镜像构建使用已验证的JDK/Maven缓存。
- Host四进程/16+4与Linux容器四进程/统一20端到端冒烟，各60次浏览全部changed、发布/消费和逐篇计数一致，真实池预算与4个独立PID核对通过。

## 发布与消费：隔离解决了什么

两轮长测，每批平均耗时如下（实际批次大小有差异，publisher满批计时另在完整JSON保留）：

| --- | ---: | ---: |

| publisher send | 76.131 | 75.528 |
| publisher confirm等待 | 6.034 | 5.763 |
| publisher batch mark（含事务） | 22.433 | 29.986 |
| consumer event调用 | 4.335 | 2.519 |
| consumer event取连接 | 1.721 | 0.002 |
| consumer apply取连接 | 0.543 | 0.001 |
| consumer apply事务体 | 42.445 | 41.418 |
| consumer提交近似耗时 | 11.242 | 10.854 |
| consumer Redis缓存失效 | 2.689 | 2.195 |

event调用包含event取连接，不能相加；apply事务体包含processed/stats SQL。事务体仍是消费主要成本，stats SQL约34.7–35.7 ms/批；Redis失效约占消费周期3.5%–4.0%。发布器send占周期55%–60%，confirm等待仅4%–5%，不能把send统称为等待Rabbit确认。

两池隔离后publisher有事件批次的claim+mark取连接总耗时从7,108.284 ms降到7.758 ms，但claim/mark包含的SQL与提交并未随之消失。后台最多2个连接同时活跃与当前单发布器、单消费者一致，预留4个连接存在未使用容量。

## JVM、WAL与checkpoint

- 全轮WAL fsync均值4.26–5.64 ms；两轮长测5.165、5.087 ms。PG/WAL区间、连接/Rabbit探针均无采集失败。JFR所选GC pause累计约占各轮墙钟0.42%–0.59%，单次最大17–27 ms，不能解释数百毫秒的多处无GC尖峰。
- R5第83秒HTTP p95 715.8 ms，取连接平均225.62 ms、commit26.49 ms，HTTP Hikari park线程累计126,410 ms，同秒没有GC pause；R7第165秒p95 408.2 ms，取连接86.45 ms、commit16.37 ms，账号/文章SQL0.73/0.72 ms，也没有GC pause。支持连接与提交路径的拥塞，而不是查询SQL本身突然变慢。
- R6第116秒p95 372.1 ms，但取连接0.04 ms、commit7.82 ms、没有GC或Hikari park；说明仍有发压/传输/入口其他阶段的慢请求，不能把所有HTTP尖峰归为数据库。完成秒归桶会把早先开始的慢请求放在较晚时间桶。
- R7第300秒属于目标窗口外在途请求尾部，仅98个完成请求，p95 1,107.4 ms；不能将这一桶视为又持续发压了一秒。R7整体p95/p99已包含这些完成请求，稳态第10–300秒分布不含该尾桶。
- 定时checkpoint开始/完成：R1 67.045→146.634秒，R7 156.253→360.645秒，R8 153.997→356.356秒。三轮after-drain前checkpoint均未完成，`num_done=0`不表示没有活动。两轮长测PG区间checkpointer实际IO write_time累计157.007、232.203 ms（包含HTTP后观察）；日志write阶段203.829、201.808秒包含分散写入阶段，不能当作连续磁盘阻塞。
- R8第10–80秒的mark慢段早于153.997秒的定时checkpoint开始，因此该checkpoint不能解释这段更早的恶化。仍缺宿主/WSL磁盘延迟、CPU调度时间轴及专用主机复现，当前未证明物理磁盘或WSL调度是哪一个根因。
