# 文章指标发布器拆测（2026-09-26）

## 结论

本轮异步排空的主要耗时是**逐条 `markPublished`**：混合有效写占发布器批次执行时间的 **96.17%**，匿名浏览占 **97.05%**。请求结束后，每条标记仍平均耗时 **7.86 / 8.00 ms**，而这些标记的借连接耗时合计仅 **3.57 / 2.95 ms**。因此，连接池排队能解释 HTTP 突发阶段的部分等待，却不能解释之后约 80 秒的发布积压。

`claimOutbox(200)` 在请求结束后的完整批次中，p50 约 **12 ms**；RabbitMQ 异步确认延迟均值约 **3 ms**，实际阻塞等确认的串行耗时占比不足 **0.03%**。最值得先改的是：把同一批中确认成功且没有 Return 的事件，一次批量标记已发布，减少数据库往返和独立提交。本轮只添加计时并复测，尚未实施该优化。

## 环境与计时边界

新建隔离 Compose 项目 `air-perf-publisher`，镜像 `air-perf-publisher:local`，应用端口 18085，RabbitMQ 管理端口 18086，均仅监听本机。独立 PostgreSQL、Redis、RabbitMQ 卷；V1004 slug 索引已应用，加载 2000 篇虚构文章及 5000 个虚构账号，关闭限流，客户端并发 100。先执行 5000 次首次浏览加 5000 次首次点赞，再执行 10000 次匿名有效浏览；两轮之间等待完全排空。登录准备时间不计入突发阶段。开发栈和以前的压测卷没有修改。

开启 `PERF_TIMING_ENABLED=true` 后，发布器输出 `PERF_ARTICLE_PUBLISHER` 批次 JSON，并与客户端毫秒级 Unix 时间戳对齐：

- `claimMs`：整个 `claimOutbox(200)` 方法调用，包含借连接、SQL、结果映射及事务提交。
- `sendMs`：每条消息准备和 `convertAndSend` 调用的累计时间；先发完这一批，再逐条检查确认。
- `confirmLatencyPerEvent`：每条消息发送准备开始至确认 Future 回调完成的时间。包含发送调用等客户端开销，并非纯 RabbitMQ 服务端耗时。
- `confirmWaitMs`：检查确认时实际阻塞及读取结果的累计时间。异步确认与发送、标记可以重叠，不能把每条确认延迟相加当作串行总耗时。
- `markMs`：逐条 `markPublished` 调用的累计时间，包含借连接、驱动、SQL 往返及自动提交。它不是数据库内部纯 SQL 执行时间。
- `claimAcquireMs` / `markAcquireMs`：上述调用内 Hikari 回调测得的借连接时间，已包含在相应阶段中，不能重复相加。
- `cycleMs`：本批执行时间；不包含批次日志序列化/输出和调度器固定延迟。批次间隙另行统计，均值约 101–104 ms，与 `fixedDelay=100` 一致。

发布逻辑仍是领取最多 200 条、批量发送、逐条核对 ACK 与 Return、逐条标记，失败延期重试。正常产品配置默认关闭计时。每轮取得 52 个非空批次，其中 49 个完整 200 条批次；冒烟验证的 1 条事件按时间戳排除。

## 全部批次结果

每轮均领取、发送、确认、标记 **10000 条**，失败 **0**。下表百分比的分母为各批次 `cycleMs` 之和，不含调度间隙。

| 阶段 | 混合：累计耗时 / 占比 | 匿名：累计耗时 / 占比 |
| --- | ---: | ---: |
| `claimOutbox` | 0.863 s / 0.99% | 0.817 s / 0.94% |
| 发送调用 | 2.406 s / 2.76% | 1.705 s / 1.97% |
| 实际确认等待 | 0.023 s / 0.026% | 0.013 s / 0.015% |
| 逐条 `markPublished` | **83.754 s / 96.17%** | **83.991 s / 97.05%** |
| 其他 | 0.046 s / 0.053% | 0.016 s / 0.018% |
| 批次执行时间合计 | 87.091 s | 86.542 s |

从第一批开始到最后一批结束的发布跨度分别为 **92.264 s / 91.837 s**。其中批次间固定延迟累计约 5 秒，也是开销，但明显小于标记耗时。

全轮单条确认延迟均值为 **3.238 / 2.935 ms**，最大 **16.744 / 15.850 ms**。单条标记均值为 **8.375 / 8.399 ms**，最大 **136.355 / 200.608 ms**。按当前实现，每批 200 次独立标记累计约 1.6 秒，随后才开始领取下一批。

## 排除突发期间的连接争用

以批次开始时间分类：`burst-or-overlap` 是在 HTTP 突发结束前开始的批次，可能包含结束之后的工作；`after-burst` 是结束之后才开始的批次。没有将跨界批次强行拆成两个时间段。

| 指标：`after-burst` | 混合 | 匿名 |
| --- | ---: | ---: |
| 批次数 / 标记数 | 47 / 9275 | 47 / 9276 |
| 标记耗时占比 | 96.49% | 97.19% |
| 单条标记均值 | 7.857 ms | 8.004 ms |
| 标记借连接累计 | 3.570 ms | 2.945 ms |
| 领取借连接累计 | 0.040 ms | 0.047 ms |
| 完整批次领取 p50 / p95 | 12.275 / 22.438 ms | 12.300 / 16.872 ms |
| 完整批次标记 p50 / p95 | 1551.648 / 1749.339 ms | 1584.104 / 1781.002 ms |
| 单条确认延迟均值 | 3.124 ms | 2.849 ms |

突发或跨界批次中，标记借连接累计为 **4.489 s / 3.214 s**；之后下降至几毫秒，但标记累计仍达 **72.878 s / 74.241 s**。这把“突发时与请求抢连接”和“排空时逐条标记慢”区分开了。

仓库中的 `markPublished(UUID)` 是一条 UPDATE，方法没有 `@Transactional`；调用方也没有将整批标记包在事务内，当前数据源使用自动提交。现有实现因而为每条标记执行一次数据库调用和独立提交。等待采样观察到 `IO:WalSync`、`LWLock:WALWrite`，与提交开销的解释一致；仅凭这些抽样还不能量化磁盘、WAL、驱动与 SQL 各自占比，也不能断言存在慢 SQL。

## 下一步建议

优先增加批量标记接口：收集已 ACK 且没有 Return 的 ID，使用一次批量 UPDATE 提交发布标记；确认失败的 ID 仍进入延期重试。数据库标记失败时保持 outbox 可重试，并依靠现有消费者幂等机制处理可能的重复投递。不要在等待 RabbitMQ 确认期间持有数据库事务。

然后在相同负载下做 A/B，比较发布器批次耗时、outbox 排空时间、连接等待、RabbitMQ 队列和最终计数。标记优化会提高入队速度，消费者的逐条事务或热点计数行可能成为新的限制；现有数据不能直接推出优化后吞吐倍数。

本轮为同机单次运行，开发栈仍在运行，包含探针和计时开销，且匿名轮在混合轮之后使用同一隔离数据库；不能将两场景差异或与旧轮 RPS 的差异当成严格性能 A/B。已完成 Java 打包、镜像构建、运行冒烟、两轮实际压测及最终正确性核对；没有将此结果表述为全量单元测试通过。测试容器已停止，独立数据卷保留。
