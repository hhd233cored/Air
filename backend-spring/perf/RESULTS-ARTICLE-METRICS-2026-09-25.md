# 文章指标压测记录（2026-09-25）

## 环境与方法

- 独立 `air-perf` Compose 栈：Spring Boot、PostgreSQL、Redis、RabbitMQ 各一个容器；与开发数据库和音乐目录隔离。
- 预置 2000 篇虚构文章、5000 个虚构普通账号，目标为 `perf-article-1`。密码哈希由隔离栈的引导账号复制，没有真实用户数据。
- 先以 4 路并发登录并取得 Redis Session 与 CSRF token；这 85.1 秒不计入文章指标请求的 13.8 秒突发阶段。
- 突发阶段最多 250 个并发用户；每人先提交一个 UUID 浏览事件，再提交一次点赞。随后同一用户并发重复点赞 100 次。
- 关闭产品限流，以测链路处理能力；HTTP 客户端与四个容器共用本机资源。下面的 RPS 是这一次客户端负载下的实测值，不代表生产容量。

## HTTP 结果

| 场景 | 请求数 | 成功与去重 | p50 | p95 | p99 |
| --- | ---: | --- | ---: | ---: | ---: |
| 浏览上报 | 5000 | 5000 次 202，均 `changed=true` | 319 ms | 624.9 ms | 810.7 ms |
| 点赞 | 5000 | 5000 次 200，均 `changed=true` | 305.9 ms | 614.4 ms | 815.6 ms |
| 同一用户重复点赞 | 100 | 100 次 200，均 `changed=false` | 25.1 ms | 44.1 ms | 48.4 ms |

两类有效写请求在同一个 13.8 秒窗口共完成 10000 次，合计约 **725 次请求/秒**。每类单独用同一窗口计算约 363 次请求/秒；它们不是两个独立运行的吞吐结果。

## 最终一致性与故障

突发结束后，点赞统计先到 5000，浏览统计随后逐步追上。排队处理期间重启隔离应用，一次统计轮询出现网络错误；恢复后第 47 次轮询读到 `viewCount=5000`、`likeCount=5000`。PostgreSQL 核对：浏览事实 5000、点赞关系 5000、已处理事件 10000、未发布 outbox 0；文章指标工作队列和死信队列的 ready/unacked 均为 0。重新读取公开统计后，Redis 快照也是 5000/5000。

另行停止隔离 RabbitMQ 后提交一次浏览：HTTP 返回 202，数据库浏览事实为 5001、未发布 outbox 为 1，统计仍为 5000。恢复 RabbitMQ 后，未发布数变为 0，已处理事件 10001，统计浏览数变为 5001。无 CSRF token 的浏览写请求返回 403；带 CSRF token 但未登录的点赞请求返回 401。

一次较早的准备阶段试跑把登录并发设为 16，Spring Session 写 Redis 时出现 1 秒命令超时和登录 500，当时应用容器瞬时约占 5 GiB。将**准备阶段**登录并发降为 4 后完成正式压测；这说明登录准备阶段有自己的资源上限，不能把其失败归因于文章指标链路。正式压测结束后的资源采样：应用约 480 MiB、PostgreSQL 89 MiB、Redis 39 MiB、RabbitMQ 116 MiB；这些是恢复后采样，不是突发阶段峰值。

脚本按用户先浏览后点赞，使用 250 并发用户而非 5000 并发连接。重启验证覆盖尚未汇总的积压事件；没有精确控制在消费者“数据库已提交但 ACK 未发出”的微小时间窗内崩溃。重复投递的数据库幂等路径另由集成测试对同一事件再次 `apply` 验证。生产容量仍需在独立机器上以固定资源限制和完整监控复测。
