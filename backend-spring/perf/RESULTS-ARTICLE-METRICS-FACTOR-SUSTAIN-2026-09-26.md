# 文章指标四组参数对照与持续负载实验

日期：2026-09-26。对应用户授权的两项实验：连接池 10/20 × 发布器每轮最多 1/4 批的四组对照，以及候选配置的 60–120 秒持续压测。本文记录实验结果；参数仅应用于隔离实验栈。

## 结果摘要

**推荐继续验证池 20 / 发布器每轮最多 4 批。** 相对池 10 / 发布 1 批，短测全批完成吞吐在匿名/混合场景分别提高 **27.0% / 19.3%**。六轮各 60 秒持续负载在实际约 **595–987 HTTP RPS** 下全部计数正确，未观察到后台积压在每 10 秒窗口持续扩大。

计划 288,000 次持续到达，实际发送并正确完成 **284,033 次**，未发送 **3,967 次**。1000 档混合漏发 3.14%，其中大部分为客户端调度迟到；不能宣称无损支持 1000 RPS。当前已测最大成本仍是 HTTP 写事务提交与偶发共享池排队；账号/文章 execute 和 Redis DEL 较短，下一轮优先分离发压机并对齐尖峰观测。

相对 10/1，20/4 的匿名 HTTP / 全批完成吞吐提高 **13.5% / 27.0%**，混合提高 **7.2% / 19.3%**。固定池 20，将发布上限 1→4，匿名全批完成提高 **13.6%**，混合提高 **12.9%**；对应 HTTP 提高较小，分别 **1.3% / 3.0%**。这符合连续发布主要减少异步供给间隔的作用。

按两场景全批完成吞吐的几何平均选择持续测试候选，20/4 得分 **830.4 事件/s**。它是这轮实验的候选参数，尚不能据此宣布生产环境最优。

消费取连接占比为 eventAcquire + applyAcquire 的总时间 / cycle 总时间。池 20 显著缓解了 HTTP 与后台任务共享池的争用；写事务 commit 没有相同幅度的下降，部分组合上升。账号/文章查询、Redis DEL 不能据此认定为主要瓶颈。

匿名发布器每批平均 claim / send / confirmWait / mark（ms）：10/1 为 **44.1 / 116.4 / 6.3 / 40.0**；20/4 为 **20.2 / 118.3 / 6.7 / 19.8**。混合分别 **39.7 / 72.4 / 3.9 / 41.5** 与 **18.2 / 91.2 / 5.7 / 17.0**。send 与确认回调存在并行，confirmWait 是发送完成后的剩余等待。池变大降低 claim/mark 的取连接成本，未消除 Rabbit 发送成本。

调度 fixedDelay 100 ms 保持不变。两轮调度之间的平均间隔约 **102–108 ms**；上限 4 时同轮批次间隔约 **1.5–2.6 ms**。上限 4 仍受 250 ms run budget、未满批和健康状态限制，不保证每轮都发布四批。Redis 批量失效平均 **1.46–4.43 ms/批**，所有批次调用一次 DEL，无失效失败。

### 短测波动

混合 20/1 两轮 HTTP 为 **781.2 / 1,151.2 RPS**，20/4 为 **771.4 / 1,266.4 RPS**。每个参数只有两轮、客户端与服务共用主机；倒序复测减少顺序偏差，但无法消除主机、缓存、GC、存储等随时间变化的影响。不能把合并提升当作精确、可复现的因果收益。

匿名本轮吞吐低于之前完整链路报告中的约 907 RPS；本轮抽样 JDBC commit 约 9–10 ms，之前约 7 ms。两次活动不在同一窗口，不以跨轮绝对数值断言代码退化。这里优先比较同一活动内的四组。

| R6 | 9.74 / 6.67 | 68.4% | 0.54 / 0.51 | 4.3% | 1.51 |

写请求直接 JDBC commit 是已测连接持有成本的主要部分；wal sync 等待有观测，WAL fsync 均值 **3.18–4.37 ms**，无死锁、未采到数据库行锁等待。共享池平均等待较小，但所有轮次都有短时排队。不能以这些均值推断全部 HTTP 尾延迟由 commit 引起。

发布 send 每批均值由 600 档约 **25–26 ms** 增至 1000 档约 **55–56 ms**；平均批量由约 **89** 增至 **167–171**，不能将每批耗时增大直接解释为每事件性能退化。调度轮间隔仍约 **101 ms**，满批连续发布减少这段空隙。当前实际负载下未看到持续 outbox 增长，没有证据要求优先重写消费者或换 Redis Lua。

第 10–60 秒窗口的 HTTP p95 依次为 **29.7 / 37.5 / 49.8 / 45.8 / 56.1 / 60.6 ms**，p99 为 **143.6 / 159.4 / 146.5 / 144.2 / 130.4 / 133.0 ms**。这是按完成时间筛选的窗口，排除了部分启动与窗口后完成请求，存在边界筛选影响，因此同时保留整轮分位数和尾部。

1000 档混合迟到漏发 **1,632 / 60,000 = 2.72%**，并发满漏发 **0.42%**，合计 **3.14%**；客户端 ELU **92.5%**、循环延迟 p99 **38.1 ms**。调度迟到和同机干扰需要先排除，当前数据没有测出可靠服务端吞吐上限。调度预算 25 ms 在准入检查时应用，实际任务回调可晚于预算，已保存真实 lateness（R4 最大 34.7 ms）。

### 两处队列采样缺口

- R3 管理接口 `fetch failed`，发生于起点后 **65.28 秒**，HTTP 已在 60.14 秒完成。
- R6 最后一处采样的数据库时刻 **60.07 秒**，Rabbit 请求在 **66.55 秒**超时返回；该样本跨越负载结束，不能将其 6.49 秒当作纯数据库等待。队列字段保留缺测。

两轮标为 **PASS_WITH_PROBE_GAPS**，业务及最终队列核对通过；另四轮 PASS。只为保存这两处真实缺测，在汇总时显式启用 `--allow-probe-gaps`；默认严格门槛仍会拒绝含缺测的输入，已验证。失败次数和原记录写入 JSON/CSV，未用零补齐，也未把管理接口超时当成业务请求失败。

持续调度器按到达时间准入，超过 25 ms 调度预算的旧到达记 droppedLate，并发满时记 droppedBusy。所有未发送到达单列，不记为 HTTP 成功或服务器业务错误。混合按“浏览后点赞”请求对准入，目标单位速率为请求 RPS/2；逐秒 startedRequests 为已准入请求对的两倍，点赞实际发起时间晚于浏览完成，可能在准入结束后。最终 startedRequests 是已发送并收集到响应的请求总数。

混合每轮登录 5,000 个账号，跨循环轮换文章，确保每个用户/文章仅首次点赞；所有浏览使用新幂等键。根据实际发送的组合计算逐篇预期计数。短测仍使用原闭环负载，持续测试增加时间调度，二者的并发和工作负载不同，不能直接相除宣称优化幅度。

## 下一步建议

1. **以 20/4 为后续验证候选**，保留耐久性设置。短测可见共享池争用明显降低，持续实际负载下后台跟得上；本轮只修改实验参数。
2. **先用独立发压进程/主机复测 1000 档并重复更长窗口**，核对目标到达是否完整。特别是混合 1000 档的调度漏发，解决后再判断服务端容量；必要时继续 5–10 分钟测试以覆盖更多 GC、checkpoint 和 autovacuum 周期。
3. **对齐尖峰时的 JVM GC、Tomcat 线程排队和数据库 commit/WAL**。持续阶段账号/文章 execute 仅约 0.5 ms，Redis DEL 约 1–2 ms/批；当前不支持把它们列为首要优化对象。Redis Lua 改变持久化/一致性设计，不能只因秒杀短路吞吐高就替换现有事实/outbox链路。

## 共同配置与口径

- 应用镜像 `air-perf-pool-http:local`，ID `sha256:20148162e6276d13220ff2735944d1c3ea8bfa76d022972cc716a44124795a20`，所有轮次一致。本轮未修改 Java 业务源码，也未重建应用镜像。
- 消费者单并发，每批最多 100、聚批最多 100 ms；发布每批最多 200、run budget 250 ms。池 maximum/minimum-idle 同步设为 10/10 或 20/20，每轮从应用核对真实配置。
- PostgreSQL 18.6，fsync/synchronous_commit 开启；Redis 8.4、RabbitMQ 4.3.6。PG IO/WAL timing 与 pg_stat_statements 开启；压测关闭限流，正常鉴权/CSRF 保留。
- Host 客户端 Windows Node v24.15.0 / Undici 7.24.4，本机回环访问；开发栈四个容器保持运行。没有独立发压机或主机资源隔离。
- 四组各独立新卷，夹具 2,000 篇文章、5,000 个账号；正文每篇 600 字符。每轮取 100 篇、使用新范围。短测各 10,000 写入、并发 100，组内历史写入数量相同，登录准备排除在计时窗口外。
- A=10/1、B=20/1、C=10/4、D=20/4。匿名顺序 **A B D C / C D B A**；混合 **C D B A / A B D C**。组内范围依次 1–100、101–200、201–300、301–400。
- 计时全量覆盖 HTTP/Tomcat/传输，JDBC 10% 随机抽样，发布/消费记录完整批次。短测过程中客户端脚本增加持续负载分支与配置字段；短测请求及计时边界保持原逻辑。
- HTTP RPS 为客户端收到完整正文的完成吞吐。全批完成事件/s 为有效事件数 / 从 burst 开始至最后消费者完成日志的时间，包含消费提交、Redis 失效和 ACK 调用返回。最终队列检查补充验证排空。
- 逐事件创建→发布标记/消费事务起点来自数据库时间戳。`now()` 为事务起点，不代表提交/Confirm/ACK完成；有 **68,618** 个短测事件的消费事务起点早于批量 published 标记起点，这属于并行顺序，不用于计算 broker 延迟。创建→消费事务起点无负数。依据 [PostgreSQL 时间函数文档](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)。
- 逐秒时间轴按请求/批次完成时刻归桶。取连接、outbox 与 Rabbit 探针并非同时执行，CSV 保留各自时间戳，缺测留空；outstandingEvents=HTTP完成累计−apply累计，可短暂为负，不能当作精确 broker 队列深度。
- PG WAL fsync 平均 **3.87–5.53 ms**；累计窗口包含全部后台和探针活动，不能直接用总耗时除以业务请求作为 commit。JDBC execute 含驱动/网络/数据库执行，hold 已包含 SQL 与 commit，不重复相加。
- 客户端短测 ELU **73.4%–99.6%**，事件循环延迟 p99 **18.9–149.3 ms**；ELU 不是 CPU 使用率。仍有响应头等待未归属余量 **10.0–108.1 ms/请求**，不能全部解释为网络或 commit。依据 [Node perf_hooks 文档](https://nodejs.org/api/perf_hooks.html)。
- 管理接口 drain 受 Rabbit 统计刷新影响；如 R4 观测到约 45 秒排空，实际批次完成远早于它。吞吐使用消费者日志而非管理轮询时刻。

调度器与 HTTP transport 共 **7 项 Node 测试通过**；覆盖并发上限、忙时/迟到漏发、唯一点赞组合、任务错误与逐秒计数守恒。PowerShell 语法解析通过；持续端到端冒烟 **20 次浏览全部写入、发布、消费且统计一致**。应用镜像沿用此前通过 56 项 Java 回归的版本，本轮未重复运行 Java 测试。

复现参数示例（需使用新项目、新 label 和未测文章范围）：

```powershell
./perf/run-metric-experiment.ps1 -Project air-perf-drain-example-new `
  -Label example-new -AppPort 18501 -RabbitPort 18502 `
  -Image air-perf-pool-http:local -PoolSize 20 -PublisherBatches 4 `
  -ConsumerBatchSize 100 -Scenario anonymous-view -ArticleCount 100 -ArticleOffset 1 `
  -DurationSeconds 60 -TargetRps 600 -Concurrency 200 `
  -JdbcTiming -JdbcSampleRate 0.1 -PostgresCounters -HttpTransportTiming -Seed -StopStack
```
