# 消费者批量统计 SQL 与 Redis 删除（2026-09-26）

## 实现

接续 [发送与多文章对照](RESULTS-ARTICLE-METRICS-PUBLISHER-DRAIN-2026-09-26.md) 的计划，减少多文章消费者的数据库和 Redis 往返：

- `ArticleStatsCache.evictBatch` 收集唯一文章键，一次 `StringRedisTemplate.delete(Collection)`，对应当前单机 Redis 的多键 DEL；空集合不调用 Redis。
- 缓存删除仍在 `applyBatch` 事务成功返回后、任何有效消息 ACK 前执行。Redis `DataAccessException` 记录失败并沿用 30–35 秒短 TTL，已提交事件继续 ACK。此行为与此前逐篇删除的兜底相同，未添加重投后必然删除成功的保证。
- `applyBatch` 先批量插入 processed 防重标记，只聚合首次处理事件；再用参数化 VALUES CTE 和一条 `INSERT … SELECT … ON CONFLICT` 更新所有受影响文章。
- 每篇文章只生成一行并按文章 ID 排序更新。VIEW 累加首次处理数量，LIKE 从关系事实重算，不按消息 delta 推算；纯 VIEW 保留已有点赞数。防重与统计仍在一次事务中提交，任一文章失败整批回滚。
- 没有新增表、迁移或业务配置，消费者仍单线程，默认批大小 100、等待 100 ms；发布器默认最大批次数仍为 1。

点赞重算使用本条 SQL 的数据库语句快照，仍是异步读模型。本次没有启用多消费者；按 ID 排序不能代替将来的并发一致性验证。缓存与数据库仍按有界陈旧语义工作，删除与并发旧读回填之间的竞态没有在此修改中解决。

## 指标与正确性验证

新增 `statsSqlCalls`、`cacheDeleteCalls` 与 `cacheEvictionFailedArticles`；`cacheArticles` 保留涉及文章数，`cacheEvictionFailures` 是失败调用数。一次批量删除失败会影响多篇文章，不能再将文章数解释为 Redis 往返次数。历史缺失字段汇总为 null。

45 个测试全部通过，无跳过：消费者 20、发布器 18、PostgreSQL 集成 4、缓存 3。集成测试使用独立随机 schema 和真实 PostgreSQL 事务，覆盖：

- 第二篇文章统计违反约束时，全部新防重标记与统计一起回滚，缓存不删除、有效消息重投。
- 重试成功时，从其他连接可见完整计数后才调用一次批量缓存删除；重复投递不再更新统计或失效缓存。
- 跨文章混合 VIEW/LIKE、同批重复事件、纯 VIEW 保留已有点赞数、新统计行、取消/重新点赞乱序、全重复与空批次。
- 缓存键去重、空集合、Redis 故障的失败调用/受影响文章指标，ACK/NACK/Return 等既有可靠性验证。

日志：`target/consumer-bulk-tests-2026-09-26.log`。通过隔离 Java 21 测试镜像运行，测试 schema 清理，不接触开发库。

## 同条件复测设计

对照为 `air-perf-publisher-drain-final:local`，候选为 `air-perf-consumer-bulk:local`。依赖、JRE、JVM 参数相同；候选只改批量统计与缓存失效及计时。每轮配置文件保存实际镜像 ID。

- 对照：`sha256:098c8142f9f11bb91f37c0bccbec3a95e023b6d814f1cf238a79be4a80407439`
- 候选：`sha256:150d27c4712f6f4aa171a87f13784e4f3eb2175ffdfb7843493869aaf9f5fa93`

独立项目 `air-perf-drain-bulk-control`（18141/18142）与 `air-perf-drain-bulk-candidate`（18151/18152），各有独立 PostgreSQL/Redis/RabbitMQ 与相同 2000 篇文章、5000 用户夹具。每次只运行一组实验栈，开发栈继续运行。

每轮 mixed 有效写 10000 次（浏览/点赞各 5000）、HTTP 并发 100、100 篇文章 round-robin，每篇预期 50 次浏览与 50 个点赞关系。批大小 100、聚批 100 ms、消费者并发 1、发布器最多 4 批/250 ms、数据库池 10、限流关闭，计时和同时间轴等待采样开启。登录准备不计入 RPS。

采用 AB、BA、AB（旧、新、新、旧、旧、新）六轮。每种实现分别使用文章 1–100、101–200、201–300，每轮前启动应用、轮后停止该项目，保留事实和卷。各组使用相同增长规模；不清库或覆盖旧记录。逐篇等待业务计数，并核对事实/统计/processed/outbox 和工作/死信队列。

统计 SQL 累计耗时减少 **81.9%**，Redis 删除减少 **97.6%**，消费累计执行减少 **47.2%**，最后 ACK 平均提前 **24.8%**。这是当前 100 篇分布和发布器最多 4 批参数下的结果，不能当作所有文章分布或默认发布器 1 批下的吞吐提升比例。

HTTP 聚合 RPS 低约 1.3%，p95 有波动，未证明请求端吞吐提升。消费事务次数没有减少，候选更及时跟上发布，部分批次不足 100；每批提交耗时也仍受共享池和 I/O 影响。这次主要收益是减少逐篇往返及 HTTP 突发后持续消费积压。

候选平均消费取连接累计 4.091 s，占消费执行 **53.8%**，集中在 HTTP 突发期间。消费者更及时处理消息后，更多工作与 HTTP 写入重叠；共享池等待成为更大的成本。这是观察到的阶段变化，尚未用独立资源实验区分策略影响与同机 I/O/调度波动。各轮采到 `IO:WalSync`、`LWLock:WALWrite`，R5 还采到 `IO:WalWrite`；未采到 `Lock` 等待不能排除瞬时锁。

六轮每篇均有 100 次 HTTP 请求、50 次浏览和 50 次点赞，逐篇正确性均通过。完成时间差是 HTTP 层面的分布检查，不能作为每篇事件提交延迟或 broker 公平性的保证。

## 判断与下一步

批量统计 SQL 和缓存删除已落地，当前多文章负载的消费者往返成本明显下降。此配置下剩余限制主要体现在 HTTP 突发时共享连接池等待、逐次事实/outbox 写事务的提交，以及发布供给速度。账号与文章查询耗时中包含取连接等待；还需要 SQL 实际执行阶段的证据才能判断其查询语句是否需要继续优化。

下一步优先将 HTTP 认证/文章定位/事实写入的连接持有时间、实际 SQL 和提交放在同一时间轴，区分借连接等待与数据库执行，并观察 I/O。保持池大小和单消费者条件做针对性实验后，再决定是否隔离异步工作资源。扩大消费者并发前，仍需验证多事务重算点赞统计的一致性和热点行锁。

本次同机资源未独占或固定配额、每组只有三轮，数据库随轮次增长；交替顺序、相同增长规模和每轮重新启动降低了部分偏差，未提供随机化或置信区间。新镜像同时改了 SQL 和 Redis 调用方式，分段计时可以显示对应成本变化，但没有两个改动分别开关的独立实验。不能由这些数字外推生产容量或归因全部 HTTP 差异。
